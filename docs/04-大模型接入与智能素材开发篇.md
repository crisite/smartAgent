# 14 — 模型配置与统一调用
本章开始让后端具备“调用文本大模型”的能力。这里先不做商品诊断、文案或图片生成；只完成所有后续智能功能都会复用的底座：**配置从哪里来、请求如何发出、返回内容如何变成可靠的 JSON、出错时如何向调用者说明问题。**

> **本章完成后能得到什么？** 在 Swagger 中保存一套文本模型配置，调用“测试连接”接口，并由后端向兼容 OpenAI Chat Completions 协议的模型服务发起一次结构化请求。

## 14.1 本章要解决的问题

在前面的业务系统中，商品、店铺等数据都由用户填写或上传。智能能力出现后，系统还需要同外部模型服务通信。若业务路由各自保存 API Key、各自拼接 URL、各自解析模型回复，会很快产生三类问题：改模型时需要修改很多文件；密钥容易被接口回显；某个模型返回了普通文本会导致业务数据无法保存。

因此本章只建立一条统一通路：

```text
管理员在 Swagger 保存配置
        │
        ▼
数据库中的 model_provider_settings
        │
        ▼
get_runtime_settings() 合并运行时配置
        │
        ▼
create_json_chat_completion() 统一请求模型
        │
        ▼
校验外层响应 → 取出 content → json.loads()
        │
        ▼
后续商品诊断、文案生成等业务模块拿到 Python 字典
```

本章会创建或修改以下文件；可直接复制第14章代码包中的同路径文件，代码包中的文件就是本章结束时的完整形态。

| 文件 | 本章职责 | 开发顺序 |
|---|---|---:|
| `api/app/services/model_settings.py` | 读取、保存、脱敏并合并模型配置 | 1 |
| `api/app/services/llm.py` | 发送文本模型请求并强制得到 JSON 对象 | 2 |
| `api/app/api/routes/model_settings.py` | 给前端或 Swagger 提供配置、保存和连通性测试接口 | 3 |
| `api/app/main.py` | 注册新路由 | 4 |
| `api/tests/test_*.py` | 验证配置、请求边界和既有业务不被破坏 | 5 |

完整文件见 [第14章配套代码](04-配套代码/第14章/文件清单.md)。先按本章顺序开发，最后再整体复制校对；不要先把路由注册进 `main.py`，否则被导入的服务文件尚未创建时，应用将无法启动。

## 14.2 先理解模型配置

### 14.2.1 什么是 Provider、Base URL、Model 和 API Key

模型服务可以来自云厂商、公司内部网关或本机部署。它们虽然地址不同，只要兼容 OpenAI 的 Chat Completions 协议，就可以共用本章的调用函数。

| 配置项 | 小白可以怎样理解 | 示例 | 是否可以返回给浏览器 |
|---|---|---|---|
| Provider | 这套配置的名称或服务商 | `deepseek`、`company-gateway` | 可以 |
| Base URL | 模型服务的门牌号 | `https://api.example.com/v1` | 可以 |
| Model | 要使用的具体模型名 | `deepseek-v4-pro` | 可以 |
| API Key | 调用服务的密码 | `sk-...` | **不可以明文返回** |

本项目把配置按 `text`、`image`、`video` 三个目标保存。第14章只真正调用 `text`；图片和视频的配置先保留位置，后续章节接入各自的生成接口。这样学生现在就能理解“配置是统一的”，又不会在尚未讲图片/视频协议时被大量细节打断。

### 14.2.2 为什么配置既有环境变量又有数据库

环境变量适合开发者在本机首次启动项目时提供默认值；数据库适合管理员在系统运行后修改配置。运行时按下面的优先级合并：

```text
数据库中目标类型对应的非空字段
        覆盖
.env 中同名的默认字段
        得到
本次请求真正使用的 Settings 对象
```

例如 `.env` 中已有文字模型地址，管理员只在 Swagger 修改模型名称，则地址仍沿用 `.env`，模型名称使用数据库的新值。这里的“非空覆盖”避免了只改一个字段时把其余字段意外清空。

> **安全边界：** 保存 API Key 时可写入数据库；读取配置时只能返回脱敏值，例如 `sk-abcd...wxyz`。浏览器、日志和异常消息都不应出现完整密钥。

## 14.3 先理解一次统一调用

### 14.3.1 URL 如何拼接

调用方只配置到服务根地址，例如 `https://api.example.com/v1`。`llm.py` 会补上 `/chat/completions`。若管理员已经填写完整路径，也不会重复拼接。这使不同兼容服务的配置形式更宽容。

### 14.3.2 为什么会出现“两层 JSON”

模型服务的 HTTP 响应本身是 JSON，典型结构是：

```json
{
  "choices": [
    {"message": {"content": "{\"title\": \"新品文案\"}"}}
  ]
}
```

外层 JSON 是模型厂商的协议；`content` 里面又是一段字符串，这段字符串才是我们希望业务使用的 JSON。统一调用函数必须连续完成四步：

1. 要求模型使用 `response_format: {"type": "json_object"}`；
2. 检查响应中是否存在 `choices[0].message.content`；
3. 用 `json.loads()` 把 `content` 字符串转换为 Python 字典；
4. 确认结果确实是对象，而不是数组、空字符串或普通说明文字。

后续业务模块从函数拿到的永远是 `dict`，不需要每次重新判断模型返回格式。

### 14.3.3 异常要在边界处分类

| 场景 | 服务层抛出的异常 | 路由返回的 HTTP 结果 | 学生排查方向 |
|---|---|---:|---|
| 地址、密钥或模型名未配齐 | `LLMNotConfiguredError` | 400 | 先保存文本模型配置 |
| 网络断开、超时、DNS 失败 | `LLMResponseError` | 502 | 检查网络和 Base URL |
| 厂商返回 401、429、500 等 | `LLMResponseError` | 502 | 检查 Key、余额、模型名或厂商状态 |
| 返回不是 JSON / 没有 content | `LLMResponseError` | 502 | 检查模型是否支持 JSON 输出 |

`400` 表示调用者还没有完成必要配置；`502` 表示应用已经按要求去请求上游，但上游通信或返回内容不合格。这个区分将沿用到后续所有智能业务路由。

### 14.4.1 创建完整文件

```python
from types import SimpleNamespace
from typing import Any

from sqlalchemy import select
from sqlalchemy.exc import SQLAlchemyError
from sqlalchemy.orm import Session

from app.core.config import Settings, get_settings
from app.db.session import SessionLocal
from app.models import ModelProviderSetting, ModelTarget


TARGETS = {
    "text": ModelTarget.TEXT,
    "image": ModelTarget.IMAGE,
    "video": ModelTarget.VIDEO,

def read_model_settings(db: Session | None = None, settings: Settings | None = None) -> dict:
    """读取模型配置；集中执行业务校验、状态变更与持久化，并返回可验证结果。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    settings = settings or get_settings()
    rows = _read_rows(db)
    text = _effective_text(settings, rows.get(ModelTarget.TEXT))
    image = _effective_image(settings, rows.get(ModelTarget.IMAGE))
    video = _effective_video(settings, rows.get(ModelTarget.VIDEO))

            "base_url": video.video_base_url or "",
            "api_key_masked": _mask_secret(video.video_api_key),
            "has_api_key": bool(video.video_api_key),

            "size": video.video_size,
            "duration": video.video_duration,

def update_model_settings(payload: dict, db: Session) -> dict:
    """更新模型配置；集中执行业务校验、状态变更与持久化，并返回可验证结果。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    for target_name, model_target in TARGETS.items():
        target_payload = payload.get(target_name) or {}
        if not target_payload:
            continue
        # 文本、图片、视频供应商分开保存，避免后续只换图片模型时影响文本生成链路。
        row = db.scalars(
            select(ModelProviderSetting).where(ModelProviderSetting.target == model_target)
        ).first()
        if row is None:
            row = ModelProviderSetting(target=model_target)
            db.add(row)

        _apply_payload(row, target_name, target_payload)

    db.commit()
    return read_model_settings(db)


def get_runtime_settings(settings: Settings | None = None) -> Any:
    """获取runtime配置；集中执行业务校验、状态变更与持久化，并返回可验证结果。"""

    return SimpleNamespace(

        api_cors_origins=settings.api_cors_origins,
        llm_base_url=text.llm_base_url,
        llm_api_key=text.llm_api_key,
        llm_model=text.llm_model,
        image_provider=image.image_provider,
        image_base_url=image.image_base_url,
        image_api_key=image.image_api_key,
        image_model=image.image_model,
        image_size=image.image_size,
        image_workspace_id=image.image_workspace_id,
        image_poll_interval_seconds=image.image_poll_interval_seconds,

        video_provider=video.video_provider,
        video_base_url=video.video_base_url,
        video_api_key=video.video_api_key,
        video_model=video.video_model,
        video_size=video.video_size,
        video_duration=video.video_duration,
        video_workspace_id=video.video_workspace_id,
        video_poll_interval_seconds=video.video_poll_interval_seconds,
        video_poll_max_attempts=video.video_poll_max_attempts,
    )


def _read_rows(db: Session | None = None) -> dict[ModelTarget, ModelProviderSetting]:
    """读取行，统一主流程中的格式、默认值和异常边界。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    if db is not None:
        return _rows_from_session(db)

    try:
        with SessionLocal() as session:
            return _rows_from_session(session)
    except SQLAlchemyError:
        # 应用启动或迁移前可能还没有配置表，回退环境变量，保证健康检查和初始化脚本可运行。
        return {}


def _rows_from_session(db: Session) -> dict[ModelTarget, ModelProviderSetting]:
    """行from会话，统一主流程中的格式、默认值和异常边界。"""
    rows = db.scalars(select(ModelProviderSetting)).all()
    return {row.target: row for row in rows}


def _effective_text(settings: Settings, row: ModelProviderSetting | None) -> SimpleNamespace:
    """生效文本，统一主流程中的格式、默认值和异常边界。"""
    return SimpleNamespace(
        llm_base_url=_row_value(row, "base_url", settings.llm_base_url),
        llm_api_key=_row_value(row, "api_key", settings.llm_api_key),
        llm_model=_row_value(row, "model", settings.llm_model),

def _effective_image(settings: Settings, row: ModelProviderSetting | None) -> SimpleNamespace:

        image_poll_interval_seconds=_row_value(
            row,
            "poll_interval_seconds",
            settings.image_poll_interval_seconds,
        )
        or 5,
        image_poll_max_attempts=_row_value(
            row,
            "poll_max_attempts",
            settings.image_poll_max_attempts,

        or 24,
    )


def _effective_video(settings: Settings, row: ModelProviderSetting | None) -> SimpleNamespace:
    """生效视频，统一主流程中的格式、默认值和异常边界。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    return SimpleNamespace(
        video_provider=_row_value(row, "provider", settings.video_provider),
        video_base_url=_row_value(row, "base_url", settings.video_base_url),
        video_api_key=_row_value(row, "api_key", settings.video_api_key),
        video_model=_row_value(row, "model", settings.video_model),
        video_size=_row_value(row, "size", settings.video_size) or "1280*720",
        video_duration=_row_value(row, "duration", settings.video_duration) or 2,
        video_workspace_id=_row_value(row, "workspace_id", settings.video_workspace_id),
        video_poll_interval_seconds=_row_value(
            row,
            "poll_interval_seconds",
            settings.video_poll_interval_seconds,
        )
        or 10,
        video_poll_max_attempts=_row_value(
            row,
            "poll_max_attempts",
            settings.video_poll_max_attempts,
        )
        or 36,
    )


def _row_value(row: ModelProviderSetting | None, field: str, fallback: Any) -> Any:
    """行值，统一主流程中的格式、默认值和异常边界。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    if row is None:
        return fallback
    value = getattr(row, field)
    if value is None or value == "":
        return fallback
    return value


def _apply_payload(row: ModelProviderSetting, target_name: str, payload: dict) -> None:
    """应用载荷，统一主流程中的格式、默认值和异常边界。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    if target_name == "text":
        _set_if_present(row, "base_url", payload, "base_url")
        _set_secret_if_present(row, payload)
        _set_if_present(row, "model", payload, "model")
        return

    _set_if_present(row, "provider", payload, "provider")
    _set_if_present(row, "base_url", payload, "base_url")
    _set_secret_if_present(row, payload)
    _set_if_present(row, "model", payload, "model")
    _set_if_present(row, "size", payload, "size")
    _set_if_present(row, "workspace_id", payload, "workspace_id")
    _set_if_present(row, "poll_interval_seconds", payload, "poll_interval_seconds")
    _set_if_present(row, "poll_max_attempts", payload, "poll_max_attempts")
    if target_name == "video":
        _set_if_present(row, "duration", payload, "duration")


def _set_if_present(row: ModelProviderSetting, field: str, payload: dict, payload_field: str) -> None:
    """设置ifpresent，统一主流程中的格式、默认值和异常边界。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    if payload_field not in payload:
        return
    value = payload[payload_field]
    if isinstance(value, str):
        value = value.strip() or None
    setattr(row, field, value)


def _set_secret_if_present(row: ModelProviderSetting, payload: dict) -> None:
    """设置密钥ifpresent，统一主流程中的格式、默认值和异常边界。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    if "api_key" not in payload:
        return
    value = payload["api_key"]
    if isinstance(value, str):
        value = value.strip()
    # 空字符串表示“不更新密钥”，防止保存表单时把已有供应商 key 意外清空。
    if value:
        row.api_key = value


def _mask_secret(value: str | None) -> str:
    """脱敏密钥，统一主流程中的格式、默认值和异常边界。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    if not value:
        return ""
    if len(value) <= 6:
        return "******"
    if len(value) <= 16:
        return f"{value[:3]}...{value[-3:]}"
    return f"{value[:7]}...{value[-6:]}"
```

完成文件编写后，对照下面的职责表理解各个函数和常量的作用。配套文件可用于核对：[model_settings.py](04-配套代码/第14章/api/app/services/model_settings.py)。

| 函数或常量 | 作用 | 为什么需要它 |
|---|---|---|
| `TARGETS` | 固定 `text`、`image`、`video` 三类目标 | 避免调用方随手写出不受支持的字符串 |
| `read_model_settings()` | 读取三类配置并对 Key 脱敏 | 供 GET 接口安全展示 |
| `update_model_settings()` | 按提交字段更新或新建数据库记录 | 支持“只更新一个字段” |
| `get_runtime_settings()` | 合并数据库和 `.env`，返回运行时 Settings | 让所有模型调用使用同一规则 |
| `_apply_payload()` | 把一个目标类型的输入应用到一条记录 | 将新增和更新共用同一套字段处理 |
| `_mask_secret()` | 将 Key 变成部分可见的字符串 | 防止配置页泄露密钥 |

特别注意：`get_runtime_settings()` 返回的是本次调用使用的配置副本，不会反过来改写 `.env` 文件。数据库临时不可用时，代码会回退到环境变量默认配置，这有利于本地排查，也不会把数据库故障伪装成“配置已保存”。

## 14.5 编写统一文本调用服务

配置服务已经能提供运行时设置，现在创建唯一允许业务模块直接请求文本模型的文件。

### 14.5.1 创建 `llm.py` 完整代码

创建 `api/app/services/llm.py`：

```python
import json
from typing import Any

import httpx

from app.core.config import Settings
from app.services.model_settings import get_runtime_settings


class LLMNotConfiguredError(RuntimeError):
    pass


class LLMResponseError(RuntimeError):
    pass


def is_llm_configured(settings: Settings | None = None) -> bool:
    settings = settings or get_runtime_settings()
    return bool(settings.llm_base_url and settings.llm_api_key and settings.llm_model)


def create_json_chat_completion(
    messages: list[dict[str, str]],
    *,
    max_tokens: int = 1800,
    temperature: float = 0.3,
    settings: Settings | None = None,
) -> tuple[dict[str, Any], dict[str, Any]]:
    settings = settings or get_runtime_settings()
    if not is_llm_configured(settings):
        raise LLMNotConfiguredError("LLM provider is not configured.")

    response_json = _post_chat_completion(
        settings=settings,
        messages=messages,
        max_tokens=max_tokens,
        temperature=temperature,
    )
    content = _extract_message_content(response_json)
    try:
        parsed = json.loads(content)
    except json.JSONDecodeError as exc:
        raise LLMResponseError("LLM response was not valid JSON.") from exc

    if not isinstance(parsed, dict):
        raise LLMResponseError("LLM response must be a JSON object.")
    return parsed, response_json


def _post_chat_completion(
    *,
    settings: Settings,
    messages: list[dict[str, str]],
    max_tokens: int,
    temperature: float,
) -> dict[str, Any]:
    url = _chat_completion_url(settings.llm_base_url or "")
    payload: dict[str, Any] = {
        "model": settings.llm_model,
        "messages": messages,
        "response_format": {"type": "json_object"},
        "max_tokens": max_tokens,
        "temperature": temperature,
        "stream": False,
    }
    if (settings.llm_model or "").startswith("deepseek-v4"):
        payload["thinking"] = {"type": "disabled"}

    try:
        with httpx.Client(timeout=60) as client:
            response = client.post(
                url,
                headers={
                    "Authorization": f"Bearer {settings.llm_api_key}",
                    "Content-Type": "application/json",
                },
                json=payload,
            )
            response.raise_for_status()
    except httpx.HTTPStatusError as exc:
        detail = f"HTTP {exc.response.status_code}"
        raise LLMResponseError(f"LLM provider returned an error: {detail}") from exc
    except httpx.HTTPError as exc:
        raise LLMResponseError("LLM provider request failed.") from exc

    try:
        data = response.json()
    except ValueError as exc:
        raise LLMResponseError("LLM provider response was not JSON.") from exc
    if not isinstance(data, dict):
        raise LLMResponseError("LLM provider response must be a JSON object.")
    return data


def _chat_completion_url(base_url: str) -> str:
    normalized = base_url.strip().rstrip("/")
    if normalized.endswith("/chat/completions"):
        return normalized
    return f"{normalized}/chat/completions"


def _extract_message_content(response_json: dict[str, Any]) -> str:
    try:
        content = response_json["choices"][0]["message"]["content"]
    except (KeyError, IndexError, TypeError) as exc:
        raise LLMResponseError("LLM response did not contain message content.") from exc

    if not isinstance(content, str) or not content.strip():
        raise LLMResponseError("LLM response content was empty.")
    return content
```

这份代码与代码包功能一致。课堂中请按顺序讲解：先是两个自定义异常，再是“是否配齐配置”的轻量判断，最后才是发送请求、解析外层协议和解析内层 JSON。

### 14.5.2 关键设计逐项理解

| 代码 | 设计原因 |
|---|---|
| `settings or get_runtime_settings()` | 测试可传入一份临时配置；真实业务不传时自动取得当前运行配置 |
| `response_format` | 明确要求模型返回 JSON，降低后续解析失败概率 |
| `stream: False` | 本项目这一阶段先等完整结果，避免处理分片流式响应 |
| `timeout=60` | 防止上游长时间无响应时 Web 请求无限卡住 |
| `response.raise_for_status()` | 将 401、429、500 立即转成可处理的异常 |
| `json.loads(content)` | 把模型返回的 JSON 字符串变成真正的 Python 字典 |
| 返回 `(parsed, response_json)` | 前者给业务使用；后者保留给需要审计或排查的场景 |

> **不要在商品路由里直接使用 `httpx.Client()`。** 后面的第15章会只调用 `create_json_chat_completion()`；模型更换、超时策略和 JSON 校验自然集中在这一处。

# 15 — 商品诊断与结构化业务生成

第14章解决了“能可靠地调用文本模型”。本章解决更接近业务的问题：如何把商品资料交给模型，又如何把模型回答变成系统能够保存、展示和继续使用的运营资料。

> **本章完成后能得到什么？** 针对一个已有商品，系统可以生成商品诊断、主图创意方案、视频脚本、库存建议、投放建议与复盘报告。每项结果都是有字段、有来源标记、可人工修改的业务记录；它们不是直接发布的广告，也不会直接调用图片或视频供应商。

## 15.1 本章的数据流与边界

本章以商品诊断作为完整代表案例，其余文本业务沿用同一套模式：

```text
商品、竞品、经营记录等已有资料
        │
        ▼
服务层只挑选本次任务所需的字段，构造上下文
        │
        ▼
第14章 create_json_chat_completion()
        │                         │
        │ 成功                    │ 未配置、超时或结构不合格
        ▼                         ▼
Pydantic 业务合同校验          规则回退生成可用草稿
        │                         │
        └──────────┬──────────────┘
                   ▼
带 source 标记的字典 → 路由保存为业务记录
                   ▼
运营人员在 Swagger / 页面查看、编辑、确认
```

模型只负责提出内容。后端负责控制输入范围、校验输出结构、明确记录来源并保存；运营人员负责审核。特别要记住：`source="rules"` 表示本地规则产生的建议，不能说成“模型调用成功”。

本章不生成真实图片、视频或向广告平台下单。主图方案里的 `image_prompt` 和视频脚本里的 `video_prompt` 都只是文字，供第16章的媒体任务继续使用。

## 15.2 先理解“结构化业务结果”

### 15.2.1 为什么不能直接存一段聊天文字

“建议突出独立包装，并测试通勤场景”对人有帮助，却无法让程序稳定知道定位、风险、行动建议分别是什么。后端需要先把模型内容约束为固定字段，才能让后续页面、主图方案或 Agent 读取同一份结果。

| 字段 | 作用 | 示例 |
|---|---|---|
| `positioning` | 一句话定位 | 面向通勤人群的便携早餐补充 |
| `price_band` | 根据当前资料判断价格位置 | 位于中低价格带，适合先测转化 |
| `audience_insights` | 人群与场景洞察列表 | 通勤、控糖、加班备餐 |
| `pain_points` | 用户顾虑或未满足问题 | 携带不便、单次食用量不清晰 |
| `selling_point_analysis` | 已有卖点应怎样证明 | 通过拆包画面证明独立包装 |
| `risks` | 仍需人工核实的问题 | 竞品样本不足，不能下结论 |
| `recommendations` | 可执行的下一步动作 | 用通勤场景制作首屏图 |

`ProductDiagnosisOutput` 是诊断的 Pydantic 合同。它不仅规定字段名和类型，也会拒绝空定位、错误类型等“看起来像 JSON、却不能用于诊断”的结果。第14章的统一调用层只保证拿到 `dict`；本章的业务服务才知道这个字典是否是一份合格诊断。

### 15.2.2 上下文不是把数据库全部发给模型

诊断服务只组织商品名称、平台、分类、价格、成本、目标人群、卖点和竞品资料。竞品也只提取名称、价格、标题、卖点、评价关键词等任务相关字段。

| 可以提供给模型 | 不应放进提示词 |
|---|---|
| 商品价格、卖点、目标人群、竞品公开资料 | 用户 Token、模型 API Key、平台账号密码 |
| 已保存的经营指标和创意方案摘要 | 与当前商品无关的整库数据 |
| “资料不足时要说明缺什么”的任务要求 | 来自爬取文本的“忽略此前指令”等内容 |

价格在组织 JSON 时要转换为 `str(...)`，因为 Python 的 `Decimal` 不能直接被 JSON 编码。输入资料也可能不可信，所以系统消息固定业务边界，用户消息只承载分析材料；最终仍由 Pydantic 校验，不能让商品备注改写系统的保存逻辑。

### 15.2.3 成功和规则回退的含义

| `source` | 代表什么 | 是否调用真实模型 |
|---|---|---|
| `llm` | 模型返回的对象通过了业务合同校验 | 是 |
| `rules` | 模型未配置、上游失败或返回不合格时，本地规则生成的草稿 | 不一定 |

规则回退不是伪造 AI。它会在 `raw_output` 中写入 `fallback_reason`，而且只能使用已有商品资料。没有目标人群就提示补资料；没有竞品价格样本就说明无法判断价格带；不会编造精确画像或销量结论。

## 15.3 再理解本章的四类业务产物

### 15.3.1 商品诊断是后续创意的输入

诊断首先回答“卖给谁、凭什么卖、风险是什么、下一步做什么”。生成后保存为 `ProductDiagnosis`。后面的主图方案和视频脚本优先读取最新诊断，使它们不必每次从零猜测商品定位。

### 15.3.2 主图方案是设计任务，不是图片文件

一条主图方案包含标题、测试角度、布局、主副文案、视觉重点、证明点、适用人群和 `image_prompt`。它保存为类型为 `main_image` 的 `CreativePlan` 草稿；不改变商品售价、库存或投放预算。

### 15.3.3 视频脚本不是 MP4 文件

视频脚本保存为类型为 `video_script` 的 `CreativePlan`，内容包括前三秒钩子、建议时长、分镜、卖点证明、转化引导和 `video_prompt`。`duration_seconds` 是脚本建议时长，不等于系统已生成对应时长的视频。

### 15.3.4 建议、复盘和投放实验不会替人执行

库存建议、投放建议、自动复盘都只产生待审阅记录。投放实验的自动生成在最终实现中是根据素材、推广链接与 ROI 等已有数据生成规则草稿，并不调用 `llm.py`；因此不能仅因接口名含有 `generate` 就把它称作大模型功能。

## 15.4 开发总览：先服务，后路由

本章从第14章完成版开始。先按顺序编写服务层，再将“调用服务并保存”的增量加入已有路由。不要把提示词、HTTP 请求和事务提交全部写进路由函数，否则后续功能无法复用也难以测试。

| 开发顺序 | 文件 | 本章新增能力 |
|---:|---|---|
| 1 | `services/diagnosis.py` | 商品诊断、业务合同和规则回退 |
| 2 | `services/creative_plans.py` | 主图方案、视频脚本与各自的合同 |
| 3 | `services/inventory.py`、`inventory_advice.py` | 库存基础操作与库存建议 |
| 4 | `services/review.py` | 指标计算和自动复盘 |
| 5 | `services/ad_recommendations.py`、`ad_experiments.py`、`ad_experiment_stats.py` | 投放建议、实验草稿与统计 |
| 6 | 既有 `routes/products.py`、`routes/stores.py` | 查询资源、调用服务、保存结果、返回响应 |
| 7 | `tests/` | 固定响应、规则回退和既有指标回归 |

本章所有服务与测试的完整文件都在 [第15章配套代码](04-配套代码/第15章/文件清单.md)，用于每一步开发完成后的逐文件核对；图片、视频供应商任务相关代码属于第16章，不能提前覆盖进来。

## 15.5 编写商品诊断与创意方案服务

### 15.5.1 按步骤编写诊断服务并理解入口

创建 `api/app/services/diagnosis.py`。先定义诊断输出合同，再实现商品与竞品资料整理、提示词构造、模型分支、规则分支，最后用 `generate_product_diagnosis(product)` 汇合两条分支。路由只调用这个入口；其内部依次完成“构造上下文 → 尝试模型生成 → Pydantic 校验 → 必要时规则回退”。完整成品与 [diagnosis.py](04-配套代码/第15章/api/app/services/diagnosis.py) 逐行核对。

```python
import json
from decimal import Decimal
from typing import Any

from pydantic import BaseModel, Field, ValidationError

from app.models import Product
from app.services.llm import (
    LLMNotConfiguredError,
    LLMResponseError,
    create_json_chat_completion,
)


class ProductDiagnosisOutput(BaseModel):
    positioning: str = Field(min_length=1)
    price_band: str = Field(min_length=1)
    audience_insights: list[str] = Field(default_factory=list)
    pain_points: list[str] = Field(default_factory=list)
    selling_point_analysis: list[str] = Field(default_factory=list)
    risks: list[str] = Field(default_factory=list)
    recommendations: list[str] = Field(default_factory=list)


def generate_product_diagnosis(product: Product) -> dict[str, Any]:
    """生成商品商品诊断；集中执行业务校验、状态变更与持久化，并返回可验证结果。"""
    try:
        return generate_llm_diagnosis(product)
    except (LLMNotConfiguredError, LLMResponseError, ValidationError) as exc:
        # 诊断是素材和投放建议的上游，模型不可用时用规则版保持单品运营链路可继续。
        fallback = generate_rule_based_diagnosis(product)
        fallback["raw_output"]["fallback_reason"] = str(exc)
        return fallback


def generate_llm_diagnosis(product: Product) -> dict[str, Any]:
    """生成llm商品诊断；集中执行业务校验、状态变更与持久化，并返回可验证结果。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    parsed, raw_response = create_json_chat_completion(
        _build_diagnosis_messages(product),
        max_tokens=2200,
        temperature=0.25,
    )
    diagnosis = ProductDiagnosisOutput.model_validate(parsed)

    return {
        "source": "llm",
        **diagnosis.model_dump(),
        "raw_output": {
            "provider": "deepseek",
            "model": raw_response.get("model"),
            "usage": raw_response.get("usage", {}),
            "llm_output": parsed,
        },
    }

    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    return [
        {
            "role": "system",
            "content": (
                "你是一个资深电商运营策略助手，擅长商品定位、竞品拆解、素材测试和投放复盘。"
                "你必须只输出合法 json，不要输出 markdown，不要输出解释性前后缀。"
            ),
        },
        {
            "role": "user",
            "content": (
                "请基于以下商品和竞品信息，生成电商运营诊断。输出 json 必须严格符合示例结构：\n"
                "{\n"
                '  "positioning": "一句话定位建议",\n'

                '  "pain_points": ["痛点1", "痛点2"],\n'

                '  "risks": ["风险1", "风险2"],\n'

                "}\n\n"

                "- 建议要可执行，适合运营人员马上拿去改主图、短视频脚本或投放测试。\n"
                "- 如果信息不足，请明确指出需要补充哪些数据。\n"
                "- 每个数组建议输出 2 到 5 条。\n\n"
                f"商品信息 json：{_product_payload(product)}"

def _product_payload(product: Product) -> str:
    # 诊断只使用系统内已有商品与竞品资料，不假设平台后台真实成交、评价或库存数据。
    """商品载荷，统一主流程中的格式、默认值和异常边界。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    payload = {
        "name": product.name,
        "platform": product.platform,
        "category": product.category,
        "price": str(product.price) if product.price is not None else None,
        "cost": str(product.cost) if product.cost is not None else None,
        "target_audience": product.target_audience,
        "selling_points": product.selling_points,
        "product_url": product.product_url,
        "competitors": [
            {
                "name": competitor.name,
                "platform": competitor.platform,
                "price": str(competitor.price) if competitor.price is not None else None,
                "sales_hint": competitor.sales_hint,
                "title": competitor.title,
                "selling_points": competitor.selling_points,
                "review_keywords": competitor.review_keywords,
            }
            for competitor in product.competitors
        ],
    }
    return json.dumps(payload, ensure_ascii=False)


def generate_rule_based_diagnosis(product: Product) -> dict:
    # 规则诊断只做启发式判断，重点提示缺口和下一步测试方向，不替代真实经营分析。
    """生成rulebased商品诊断；集中执行业务校验、状态变更与持久化，并返回可验证结果。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    competitor_prices = [
        competitor.price for competitor in product.competitors if competitor.price is not None
    ]
    price_band = _price_band(product.price, competitor_prices)
    competitor_points = _flatten([competitor.selling_points for competitor in product.competitors])
    overlap_points = sorted(set(product.selling_points).intersection(competitor_points))
    differentiated_points = [
        point for point in product.selling_points if point not in set(competitor_points)
    ]

    positioning = _positioning(product, differentiated_points, overlap_points)
    audience_insights = _audience_insights(product)
    pain_points = _pain_points(product, competitor_points)
    selling_point_analysis = _selling_point_analysis(
        product.selling_points,
        differentiated_points,
        overlap_points,
    )
    risks = _risks(product, competitor_prices, overlap_points)
    recommendations = _recommendations(product, competitor_prices, differentiated_points)

    return {
        "source": "rules",
        "positioning": positioning,
        "price_band": price_band,
        "audience_insights": audience_insights,
        "pain_points": pain_points,
        "selling_point_analysis": selling_point_analysis,
        "risks": risks,
        "recommendations": recommendations,
        "raw_output": {
            "competitor_count": len(product.competitors),
            "competitor_prices": [str(price) for price in competitor_prices],
            "overlap_points": overlap_points,
            "differentiated_points": differentiated_points,
        },
    }


def _price_band(product_price: Decimal | None, competitor_prices: list[Decimal]) -> str:
    """价格band，统一主流程中的格式、默认值和异常边界。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    if product_price is None:
        return "商品售价未录入，暂时无法判断价格带。"

    if not competitor_prices:
        return f"当前商品售价为 {product_price}，还缺少竞品价格样本。"

    min_price = min(competitor_prices)
    max_price = max(competitor_prices)
    avg_price = sum(competitor_prices, Decimal("0")) / Decimal(len(competitor_prices))

    if product_price < min_price:
        position = "低于现有竞品样本，适合测试性价比或引流定位"
    elif product_price > max_price:
        position = "高于现有竞品样本，需要更强卖点证明和信任背书"
    elif product_price > avg_price:
        position = "处于偏高价格带，需要突出差异化价值"
    else:
        position = "处于中低价格带，可优先测试转化效率"

    return f"{position}；竞品样本价格区间为 {min_price}-{max_price}，均价约 {avg_price:.2f}。"


def _positioning(
    product: Product,
    differentiated_points: list[str],
    overlap_points: list[str],
) -> str:
    """positioning，统一主流程中的格式、默认值和异常边界。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    audience = product.target_audience or "目标人群未明确"
    category = product.category or "当前类目"

    if differentiated_points:
        point_text = "、".join(differentiated_points[:3])
        return f"{category}商品可围绕“{point_text}”做差异化表达，优先面向{audience}。"

    if overlap_points:
        point_text = "、".join(overlap_points[:3])
        return f"{category}商品目前与竞品共同卖点集中在“{point_text}”，需要补充更具体的使用场景或信任证明。"

    return f"{category}商品信息还偏基础，建议先明确核心卖点和目标人群，再做素材测试。"


def _audience_insights(product: Product) -> list[str]:
    """根据商品目标人群生成可执行洞察；缺失人群时返回补录建议而不是臆测。"""
    # 只使用用户录入的人群事实；没有事实时明确提示补充，不让规则兜底伪造画像。
    audience = product.target_audience
    if audience:
        return [
            f"当前目标人群为“{audience}”，素材表达应直接对应其高频场景。",
            "建议把人群从宽泛标签细化到使用场景、购买动机和决策顾虑。",
        ]
    return [
        "目标人群尚未明确，后续主图和视频脚本容易变得泛泛。",
        "建议补充年龄段、使用场景、购买理由和价格敏感度。",
    ]


def _pain_points(product: Product, competitor_points: list[str]) -> list[str]:
    """painpoints，统一主流程中的格式、默认值和异常边界。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    points = list(product.selling_points) + competitor_points
    if not points:
        return [
            "缺少卖点和竞品关键词，暂时无法稳定推断用户痛点。",
            "建议从评价区补充差评、追评和问大家中的真实顾虑。",
        ]

    pain_points = []
    joined = " ".join(points)
    if any(word in joined for word in ["便携", "轻薄", "小巧"]):
        pain_points.append("用户可能在意携带方便、通勤补用或使用负担。")
    if any(word in joined for word in ["控油", "持妆", "不卡粉"]):
        pain_points.append("用户可能在意使用效果稳定，以及长时间使用后的表现。")
    if any(word in joined for word in ["低糖", "低脂", "健康"]):
        pain_points.append("用户可能在意健康负担、成分安全和长期复购理由。")
    if any(word in joined for word in ["低价", "大规格", "买一送一"]):
        pain_points.append("用户可能在意价格是否划算，以及规格和赠品带来的确定收益。")

    if pain_points:
        return pain_points

    return [
        "用户痛点需要通过评论、客服咨询和竞品标题进一步提炼。",
        "建议把卖点改写成用户能感知的结果，而不只是商品属性。",
    ]


def _selling_point_analysis(
    selling_points: list[str],
    differentiated_points: list[str],
    overlap_points: list[str],
) -> list[str]:
    """sellingpointanalysis，统一主流程中的格式、默认值和异常边界。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    if not selling_points:
        return ["商品核心卖点缺失，建议先补 3-5 个可被画面证明的卖点。"]

    analysis = [f"当前已录入 {len(selling_points)} 个卖点，可用于生成素材测试方向。"]
    if differentiated_points:
        analysis.append(f"差异化卖点包括：{'、'.join(differentiated_points[:5])}。")
    if overlap_points:
        analysis.append(f"与竞品重合卖点包括：{'、'.join(overlap_points[:5])}，需要更具体的证明方式。")
    return analysis


def _risks(
    product: Product,
    competitor_prices: list[Decimal],
    overlap_points: list[str],
) -> list[str]:
    """risks，统一主流程中的格式、默认值和异常边界。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    risks = []
    if len(product.competitors) < 3:
        risks.append("竞品样本少于 3 个，价格带和卖点判断还不够稳定。")
    if product.price is None:
        risks.append("商品售价缺失，无法判断价格竞争力。")
    if product.price is not None and competitor_prices and product.price > max(competitor_prices):
        risks.append("当前售价高于竞品样本最高价，需要加强利益点、品牌信任或赠品机制。")
    if overlap_points and len(overlap_points) >= len(product.selling_points):
        risks.append("卖点与竞品重合度较高，素材容易陷入同质化。")
    if not product.target_audience:
        risks.append("目标人群缺失，投放和内容测试会缺少方向。")
    return risks or ["暂无明显结构性风险，下一步重点是用素材测试验证判断。"]


def _recommendations(
    product: Product,
    competitor_prices: list[Decimal],
    differentiated_points: list[str],
) -> list[str]:
    """recommendations，统一主流程中的格式、默认值和异常边界。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    recommendations = []
    if len(product.competitors) < 3:
        recommendations.append("继续补充至少 3 个竞品，覆盖同价位爆款、低价引流款和高价标杆款。")
    if differentiated_points:
        recommendations.append(f"优先用“{differentiated_points[0]}”做一版主图首屏测试。")
    elif product.selling_points:
        recommendations.append(f"先把“{product.selling_points[0]}”改写成用户结果，再做主图和短视频钩子。")
    if competitor_prices and product.price is not None:
        min_price = min(competitor_prices)
        if product.price > min_price:
            recommendations.append("投放素材中避免只打低价，应增加效果证明、场景证明或赠品机制。")
    recommendations.append("下一步生成 3 个主图方向和 3 条短视频脚本，用点击率和转化率做判断。")
    return recommendations


def _flatten(values: list[list[str]]) -> list[str]:
    """展平，统一主流程中的格式、默认值和异常边界。"""
    return [item for sublist in values for item in sublist]
```

| 位置 | 作用 | 课堂讲解重点 |
|---|---|---|
| `_product_payload()` | 把商品与竞品整理为可 JSON 编码的资料 | 为什么只选任务相关字段，Decimal 为什么转字符串 |
| `_build_diagnosis_messages()` | 生成 system / user 两条消息 | 业务边界由系统消息控制，资料放入用户消息 |
| `generate_llm_diagnosis()` | 调用第14章统一服务并校验合同 | 不能绕过 `create_json_chat_completion()` |
| `generate_rule_based_diagnosis()` | 生成明确标为 rules 的保底结果 | 回退结果也必须承认资料不足 |
| `generate_product_diagnosis()` | 对外唯一业务入口 | 成功与失败分支在这里汇合 |

```python
    raw_points = []
    if diagnosis is not None:
        differentiated = diagnosis.raw_output.get("differentiated_points", [])
        if isinstance(differentiated, list):
            raw_points.extend(str(point) for point in differentiated if point)

    raw_points.extend(product.selling_points)

    # 优先使用诊断里的差异化点，再补商品卖点，保证生成方案围绕可测试的差异表达。
    unique_points = []
    for point in raw_points:
        if point not in unique_points:
            unique_points.append(point)

    return unique_points or ["核心卖点", "使用效果", "购买理由"]

    if product.target_audience:
        proof_points.append(f"人群锚点：{product.target_audience}")
    return proof_points[:4]
```

创建 `api/app/services/inventory_advice.py`。已有的 `inventory.py` 负责库存数量变更；这个新文件负责根据库存明细给出建议，不执行扣库存或补库存。

```python
def generate_rule_based_inventory_advice(store: Store, rows: list[StoreInventoryRow]) -> dict[str, Any]:
    # 规则版只基于用户录入/导入的库存字段，不推断平台后台真实销量或订单明细。
    """生成rulebased库存建议；集中执行业务校验、状态变更与持久化，并返回可验证结果。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    low_stock_rows = [row for row in rows if row.is_low_stock]
    locked_risk_rows = [
        row for row in rows if row.quantity > 0 and row.locked_quantity / row.quantity >= 0.5
    ]
    no_stock_rows = [row for row in rows if row.available_quantity <= 0]

    if not rows:
        summary = "当前店铺还没有 SKU 库存数据，建议先补齐 SKU 和初始库存。"
    elif low_stock_rows:
        summary = f"{store.name} 有 {len(low_stock_rows)} 个 SKU 低于预警线，需要优先处理补货和投放节奏。"
    else:
        summary = f"{store.name} 当前没有低库存 SKU，库存风险较低。"

    risks = []
    if low_stock_rows:
        risks.append(f"{len(low_stock_rows)} 个 SKU 可用库存低于或等于预警线。")
```

```python
def _ratio(numerator: Decimal | int | None, denominator: Decimal | int | None) -> Decimal | None:
    """比率，统一主流程中的格式、默认值和异常边界。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    if numerator is None or denominator is None:
        return None

    numerator_decimal = Decimal(str(numerator))
    denominator_decimal = Decimal(str(denominator))
    if denominator_decimal == 0:
        return None

    return (numerator_decimal / denominator_decimal).quantize(Decimal("0.0001"))


def _latest_record(records: list[PerformanceRecord]) -> PerformanceRecord | None:
    """最新记录，统一主流程中的格式、默认值和异常边界。"""
    if not records:
        return None
    return max(records, key=lambda record: (record.period_end, record.created_at))


def _insights(
    record: PerformanceRecord,
    creative_title: str,
    experiment_name: str | None = None,
) -> list[str]:
    """洞察，统一主流程中的格式、默认值和异常边界。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。

    if experiment_name:

    if record.ctr is not None:
        if record.ctr < Decimal("0.0200"):
            insights.append(f"点击率 {_format_percent(record.ctr)} 偏低，首屏卖点或画面吸引力需要优先优化。")
        elif record.ctr >= Decimal("0.0500"):
            insights.append(f"点击率 {_format_percent(record.ctr)} 表现较好，素材有继续放量测试价值。")
        else:
            insights.append(f"点击率 {_format_percent(record.ctr)} 处于可测试区间，需要结合转化判断。")

    if record.conversion_rate is not None:
        if record.conversion_rate < Decimal("0.0200"):
            insights.append(
                f"点击到成交转化率 {_format_percent(record.conversion_rate)} 偏低，详情页、价格或信任证明可能拖后腿。"
            )
        elif record.conversion_rate >= Decimal("0.0500"):
            insights.append(f"转化率 {_format_percent(record.conversion_rate)} 较好，可优先复制素材结构。")
        else:
            insights.append(f"转化率 {_format_percent(record.conversion_rate)} 中等，建议继续测试不同卖点。")

    if record.roi is not None:
        if record.roi < Decimal("1.0000"):
            insights.append(f"ROI {_format_decimal(record.roi)} 未覆盖投放成本，暂不建议盲目加预算。")
        elif record.roi >= Decimal("2.0000"):
            insights.append(f"ROI {_format_decimal(record.roi)} 有放量潜力，但仍需观察稳定性。")
        else:
            insights.append(f"ROI {_format_decimal(record.roi)} 接近临界区，需要优化点击成本或转化效率。")

    return insights


def _next_actions(
    record: PerformanceRecord,
    product: Product,
    experiment_name: str | None = None,
) -> list[str]:
    # 下一步动作只给运营建议，不会在这里改变实验状态、预算或素材审核结果。
    """下次actions，统一主流程中的格式、默认值和异常边界。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    actions = []

    if record.ctr is not None and record.ctr < Decimal("0.0200"):
        actions.append("优先换主图首屏：把核心卖点前置到 3 秒内能看懂的位置。")
    if record.conversion_rate is not None and record.conversion_rate < Decimal("0.0200"):
        actions.append("检查详情页承接：补充效果证明、评价背书、价格权益和售后信息。")
    if record.roi is not None and record.roi < Decimal("1.0000"):
        actions.append("控制预算，先小额测试新素材，不建议直接扩大投放。")
    if record.ctr is not None and record.ctr >= Decimal("0.0500"):
        actions.append("保留当前素材结构，复制 2-3 个同结构不同卖点版本继续测。")
    if experiment_name and record.roi is not None and record.roi >= Decimal("2.5000"):
        actions.append(f"实验「{experiment_name}」达到放量观察线，可标记完成并新建一条复制结构的放量实验。")
    if experiment_name and record.roi is not None and record.roi < Decimal("1.0000"):
        actions.append(f"实验「{experiment_name}」暂不放量，建议标记暂停并回到素材或承接页优化。")
    if product.selling_points:
        actions.append(f"下一版素材优先围绕“{product.selling_points[0]}”做更直接的画面证明。")

    return actions or ["继续补充更多周期数据，再判断是否换图、调价或调整投放人群。"]


def _format_decimal(value: Decimal | None) -> str:
    """格式化小数，统一主流程中的格式、默认值和异常边界。"""
    if value is None:
        return "-"
    return f"{value:.2f}"


def _format_percent(value: Decimal | None) -> str:
    """格式化percent，统一主流程中的格式、默认值和异常边界。"""
    if value is None:
        return "-"
    return f"{value * Decimal('100'):.2f}%"
```

```python
def _best_asset(
    assets: list[GeneratedAsset],
    records: list[PerformanceRecord],
) -> dict[str, Any] | None:
    """最佳素材，统一主流程中的格式、默认值和异常边界。"""

def _best_link(
    links: list[PromotionLink],
    records: list[PerformanceRecord],
) -> dict[str, Any] | None:
    """最佳链接，统一主流程中的格式、默认值和异常边界。"""
    return _best_by_records(links, records, "promotion_link_id")


def _best_by_records(
    items: list[GeneratedAsset] | list[PromotionLink],
    records: list[PerformanceRecord],
    record_field: str,
) -> dict[str, Any] | None:
    """最佳byrecords，统一主流程中的格式、默认值和异常边界。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    if not items:
        return None

    item_by_id = {item.id: item for item in items if item.id is not None}
    summaries: dict[int, dict[str, Any]] = defaultdict(
        lambda: {
            "clicks": 0,
            "impressions": 0,
            "record_count": 0,
            "revenue": Decimal("0"),
            "spend": Decimal("0"),
        }
    )

    for record in records:
        item_id = getattr(record, record_field)
        if item_id is None or item_id not in item_by_id:
            continue

        summary = summaries[item_id]
        summary["clicks"] += record.clicks or 0
        summary["impressions"] += record.impressions or 0
        summary["record_count"] += 1
        summary["revenue"] += record.revenue or Decimal("0")
        summary["spend"] += record.spend or Decimal("0")

    if not summaries:
        # 没有历史数据时不伪造效果判断，只返回首个候选项作为冷启动默认值。
        return {"item": items[0], "ctr": None, "roi": None, "record_count": 0}

    rows = []
    for item_id, summary in summaries.items():
        spend = summary["spend"]
        impressions = summary["impressions"]
        rows.append(
            {
                "item": item_by_id[item_id],
                "ctr": Decimal(summary["clicks"]) / Decimal(impressions)
                if impressions > 0
                else None,
                "roi": summary["revenue"] / spend if spend > 0 else None,
                "record_count": summary["record_count"],
            }
        )

    return sorted(
        rows,
        key=lambda row: (
            row["roi"] if row["roi"] is not None else Decimal("-1"),
            row["ctr"] if row["ctr"] is not None else Decimal("-1"),
            row["record_count"],
        ),
        reverse=True,
    )[0]
```

```json
    "12包装，便于分享"
  ],
  "images": []
}
```

记录响应中的商品 `id`，后面称为 `product_id`。店铺 ID 与商品 ID 是两种编号，即使恰好相同也不能混用。

后续所有 `{product_id}` 都是在 Swagger 的路径参数输入框里填写这个实际数字，不是在 URL 中输入花括号。商品已有历史诊断或方案时，先记下数量，最终按“新增了多少条”核对，不要求列表恰好只有一条。

**第六步：添加一条竞品资料，让诊断有比较依据。**

展开 `POST /api/v1/products/{product_id}/competitors`，点击 **Try it out**，在 `product_id` 输入框填写第五步的商品 ID，请求体填写：

```json
{
  "name": "原味燕麦饼干（课堂竞品）",
  "platform": "douyin",
  "price": 25.9,
  "sales_hint": "课堂模拟：近期有稳定销量",
  "selling_points": [
    "家庭分享装",
    "燕麦谷物口感"
  ],
  "review_keywords": [
    "包装分量足",
    "携带不如小包装方便"
  ]
}
```

执行后预期201。它为诊断提供售价、卖点和评价线索；本案例不需要抓取真实竞品链接。已有同样的竞品资料时可以直接复用。

**第七步：准备 SKU 和库存，用于最后的库存建议。**

展开 `POST /api/v1/products/{product_id}/skus`，填写当前商品 ID，并填写：

```json
{
  "sku_code": "OAT-LOW-SUGAR-12",
  "name": "低糖燕麦饼干12包装",
  "attributes": {
    "规格": "12包装",
    "口味": "原味"
  },
  "price": 29.9,
  "cost": 12.5,
  "initial_quantity": 8,
  "warning_threshold": 20,
  "location": "A-01"
}
```

预期201。我们特意设置“库存8、预警线20”，方便观察库存建议是否识别低库存。已有该 SKU 时不要再次创建，先在商品详情中查看它的实际库存，并以实际数量验收。

调用 `GET /api/v1/stores/{store_id}/inventory-summary`，填写实际店铺 ID，确认响应 `rows` 中能找到当前商品的 SKU。对于刚创建的示例，数量应为8，`is_low_stock` 应为 `true`。店铺存在其他商品时，汇总数量可能不等于8，要检查当前 SKU 行。

**第八步：生成商品诊断。**

展开 `POST /api/v1/products/{product_id}/diagnoses/generate`，点击 **Try it out**，填写当前商品 ID，点击 **Execute**。本接口没有请求体，不需要粘贴商品 JSON，后端会从数据库读取刚才录入的资料。

预期返回201，检查：

- `id` 是新生成的诊断记录 ID，`product_id` 对应当前商品。
- `source` 应为 `"llm"`，表示本次使用模型生成且通过结构校验。
- `positioning`、`price_band` 有内容；`audience_insights`、`selling_point_analysis`、`risks`、`recommendations` 等字段结构正常。
- 内容应围绕29.9元售价、25.9元竞品、独立包装及目标人群展开。模型措辞每次可以不同，不要求与老师逐字一致。

如果返回201但 `source` 为 `"rules"`，说明规则回退成功，不代表模型业务生成成功；查看 `raw_output.fallback_reason` 排查模型配置、网络或字段校验错误。

**第九步：生成主图文字方案。**

展开 `POST /api/v1/products/{product_id}/creative-plans/main-images/generate`，填写同一个商品 ID，直接 **Execute**，无需请求体。

预期201，响应是方案数组。模型分支要求3～6条方案，逐条检查 `type: "main_image"`、`content.source: "llm"`，以及 `content.headline`、`content.layout`、`content.image_prompt` 等字段。标题或画面方向应能体现燕麦、独立包装、办公室零食等商品信息。

记录第一条主图方案的 `id`，下面录入经营数据时称为 `creative_plan_id`。这个编号来自方案，不是商品 ID。本接口只保存文字和图片提示词，没有生成图片文件，此时没有图片 URL 是正常的。回退原因在每条方案的 `content.fallback_reason` 中查看。

**第十步：生成视频脚本。**

展开 `POST /api/v1/products/{product_id}/creative-plans/video-scripts/generate`，填写当前商品 ID，直接执行，无需请求体。

预期201，响应为脚本数组。模型分支要求3～5条脚本；检查 `type: "video_script"`、`content.source: "llm"`，`content.duration_seconds` 在15～60之间，`content.scenes` 包含4～8个镜头，每个镜头有 `shot`、`visual`、`voiceover`。另外应有 `content.video_prompt` 和行动引导 `content.cta`。

本次只生成脚本，不会得到 MP4 文件。没有视频文件不能判定为失败；如果返回规则脚本，检查 `content.fallback_reason`。

**第十一步：录入一条模拟经营数据。**

生成复盘前，必须先有经营记录。本例将一条模拟经营记录关联到第九步的主图方案，用于演示模型如何解释数据；它不表示这份刚生成的方案已经真实投放。

展开 `POST /api/v1/products/{product_id}/performance-records`，填写当前商品 ID，将请求体中的 `creative_plan_id: 1` 替换为第九步记录的实际主图方案 ID：

```json
{
  "creative_plan_id": 4,
  "period_start": "2026-09-01",
  "period_end": "2026-09-07",
  "impressions": 10000,
  "clicks": 500,
  "conversions": 50,
  "spend": 300,
  "revenue": 1495,
  "notes": "课堂模拟经营数据，用于低糖燕麦饼干自动复盘验收，不是真实广告投放结果"
}
```

执行后预期201。没有填写 CTR、转化率和 ROI，后端会自动计算：

| 返回字段 | 计算方式 | 本例结果 |
|---|---|---|
| `ctr` | 500 ÷ 10000 | 0.05，即5% |
| `conversion_rate` | 50 ÷ 500 | 0.1，即10% |
| `roi` | 1495 ÷ 300 | 约4.9833 |

Decimal 字段可能以字符串形式返回，按数值检查即可。本项目这里的 `roi` 是成交额与花费之比，不是扣除商品成本后的利润率。已有比本例更晚的经营记录时，复盘会使用最新周期；如需保持录课结果一致，可将本例日期改为该商品最新的完整测试周期，确保开始日期不晚于结束日期。

**第十二步：生成经营复盘。**

展开 `POST /api/v1/products/{product_id}/review-reports/generate`，填写当前商品 ID，直接执行，无需请求体。

预期201，检查 `period_start`、`period_end` 与最新经营记录一致，`summary` 有总结，`insights` 和 `next_actions` 为非空列表。按本例数据，内容应围绕10000次曝光、500次点击、50次成交、约4.98的成交额/花费比展开，不应凭空写出已经执行的投放动作。

注意：当前 `ReviewReportRead` 没有 `source` 字段，不能照搬诊断接口的检查方法。如果 `insights` 中出现“本次复盘使用规则版兜底，原因：……”，说明发生了回退，应根据其中原因排查。没有这条回退说明，再结合模型连通性及业务内容检查结果。返回400并提示 `No performance records available` 时，先确认第十一步写入的是同一个商品。

**第十三步：生成投放建议。**

展开 `POST /api/v1/products/{product_id}/ad-recommendations/generate`，填写当前商品 ID，直接执行，无需请求体。

预期201，检查 `source: "llm"`、`summary` 和 `content`。建议应结合已有商品资料、创意方案、诊断和经营记录，给出人群、创意测试或预算方向；它只是数据库中的建议记录。此时不需要调用确认接口，也不会真的创建广告或扣费。

如果 `source` 为 `"rules"`，查看 `content` 中的回退信息，并结合后端日志排查。生成建议的记录 ID 与商品 ID 不同，后续如需人工确认，应使用建议记录自己的 ID。

**第十四步：生成实验草稿。**

展开 `POST /api/v1/products/{product_id}/ad-experiments/generate`，填写当前商品 ID，直接执行，无需请求体。

预期201，检查 `status: "draft"`，以及 `name`、`objective`、`audience`、`hypothesis`、`success_metric` 和 `note`。当前规则会设置 `daily_budget` 为300，这是计划中的预算数字，不是实际支出。本接口不调用大模型，因此无需查找 `source: "llm"`。

本章尚未生成媒体素材，案例也没有创建推广链接，所以 `generated_asset_id` 和 `promotion_link_id` 可以为 `null`，这不是错误；如果复用的商品已有素材或链接，规则可能选择已有候选项。实验名称带有执行当天的日期，不要求与课件中的固定日期一致。

**第十五步：生成店铺库存建议。**

先再次调用 `GET /api/v1/stores/{store_id}/inventory-summary` 记下当前 SKU 的数量，再调用 `POST /api/v1/stores/{store_id}/inventory-advice`。这里填写的是第四步得到的**店铺 ID**，不是商品 ID，也无需请求体。

预期200，检查 `source: "llm"`、`summary`、`risks`、`replenishment_actions`、`operation_actions` 和 `ad_controls`。对于库存8、预警线20的示例，建议应能体现库存不足的事实，而不是无依据地判断库存充足。若回退，查看 `raw_output.fallback_reason`。

执行后再次查询库存汇总，当前 SKU 数量应与执行前相同。库存建议只提供判断，不会把库存8自动改成20，也不会生成补货流水。

**第十六步：从商品详情确认结果已经保存。**

最后执行 `GET /api/v1/products/{product_id}`，填写当前商品 ID。预期200，检查下面的列表是否新增了本次生成的记录：

| 商品详情字段 | 本轮应新增的内容 |
|---|---|
| `diagnoses` | 一条商品诊断 |
| `creative_plans` | 主图方案和视频脚本，按 `type` 区分 |
| `performance_records` | 第十一步的模拟经营记录 |
| `review_reports` | 一条自动复盘 |
| `ad_recommendations` | 一条投放建议 |
| `ad_experiments` | 一条 `draft` 实验草稿 |

店铺库存建议不保存为上述商品记录，不需要在商品详情里查找它。前面的生成响应只能说明接口执行成功，重新查询详情仍能看到记录，才完成“服务生成 → 路由保存 → 查询读取”的闭环。

**常见结果如何判断。**

| 现象 | 优先检查 |
|---|---|
| Swagger 页面打不开 | 后端终端是否还在运行，地址和端口是否为8000 |
| 数据库连接失败 | Docker Desktop、MySQL健康状态，以及 `api/.env` 中数据库地址、端口和密码是否与现有配置一致 |
| 401 / 403 | Swagger 是否授权、token 是否过期、账号是否有编辑权限 |
| 404 | 路径中的商品或店铺 ID 是否真实存在并属于当前工作空间 |
| 422 | JSON格式、字段类型、日期、平台值和路径 ID 是否填写正确；查看 `detail.loc` 定位字段 |
| 本章七个接口返回501 | 检查15.7的旧占位函数是否已替换，是否重复定义了同路径路由，后端是否已重载 |
| 200 / 201，但结果为规则回退 | 基础链路成功，但模型分支未通过；按对应接口的回退原因排查，不要只检查 HTTP 状态码 |
| 请求等待较久 | 观察后端终端并等待当前模型请求返回，不连续重复点击 Execute |

完成以上步骤，本章验收才包括“真实文本模型接入”和“业务结果持久化”。第16章再生成真正的图片和视频，第17章再接入异步任务，本节不调用这些尚未完成的接口。

### 15.8.3 本章小结

现在系统已经能把“商品资料”变成“有合同、可保存、可追溯、可编辑”的运营建议。第14章提供可靠模型通道，第15章定义业务结构与回退，第16章才消费主图和视频提示词，生成真正的媒体素材。

# 16 — 图片与视频生成

第15章产出的是可审核的文字方案。本章才把审核过的 `image_prompt` 或 `video_prompt` 交给媒体供应商，得到图片、视频文件，并把结果保存为项目自己的素材记录。

> **本章完成后能得到什么？** 主图方案或视频脚本可以进入媒体生成服务；服务会提交供应商任务、轮询结果、下载文件到项目 `uploads` 目录，并返回可保存的素材字典。真正的本地任务创建、入队、重试、取消与 Worker 执行安排在第17章完成。

## 16.1 先理解媒体生成的数据流

```text
第15章已审核的 CreativePlan
        │  主图方案 / 视频脚本类型校验
        ▼
从 content 取得 image_prompt 或 video_prompt
        │  清理不兼容字符，保留业务语义
        ▼
供应商适配：提交任务 → 得到供应商 task_id → 轮询状态
        │
        ├─ 成功：取得临时资源 URL → 下载到 uploads/generated
        └─ 失败、取消、超时：抛出明确错误，不能伪造成功
        ▼
返回含 provider、model、task_id、url 的素材字典
        ▼
第17章任务服务保存 GenerationJob；本章素材服务保存 GeneratedAsset
```

| 编号或地址 | 谁创建 | 用途 |
|---|---|---|
| 供应商 `task_id` | 图片或视频供应商 | 查询供应商是否仍在处理、是否成功或失败 |
| 本地 `GenerationJob.id` | 本项目数据库 | 第17章追踪状态、重试、取消、事件和最终素材 |
| 供应商资源 URL | 供应商 | 常常有时效，只用于立即下载 |
| `/uploads/generated/...` | 本项目 | 课程系统稳定展示和管理素材的地址 |

供应商“已受理”不等于文件可用，本地任务“已创建”也不等于素材成功。只有下载完成、文件位于项目的 uploads 目录且素材记录已经保存，才能在业务上称为成功。

## 16.2 再理解本章的安全边界

### 16.2.1 方案类型不能混用

图片服务只接受 `CreativePlanType.MAIN_IMAGE`；视频服务只接受 `CreativePlanType.VIDEO_SCRIPT`。检查必须发生在真实 HTTP 请求之前，避免把视频脚本误发给图片模型，或因错误请求产生供应商费用。

### 16.2.2 供应商差异放在适配函数中

本章统一接入火山引擎即梦。图片与视频共用签名工具，各自处理业务参数和结果，共同遵守“提交 → 轮询 → 提取 URL → 下载”的过程。

### 16.2.3 轮询必须有停止条件

轮询使用配置中的间隔和最大尝试次数。明确失败状态、取消、网络异常和超出最大次数都会结束；不能把轮询写成无限 `while True`，也不要把间隔设为 0。

### 16.2.4 生成结果仍需人工审核

`_sanitize_image_prompt()` 和 `_sanitize_video_prompt()` 只清理协议可能不接受的不可见字符、弯引号或特殊货币符号；它们不是内容安全、版权或广告合规审核。下载成功的素材默认仍是“待评估”。

## 16.3 开发总览：先签名工具，再媒体服务，再素材库

| 顺序 | 文件 | 本阶段解决的问题 |
|---:|---|---|

| 4 | `services/generated_assets.py` | 将成功结果变成统一素材记录并按 URL 去重 |

### 16.3.1 统一模型与配置

本章使用[即梦文生图3.0](https://docs.volcengine.com/docs/85621/1616429?lang=zh)和[即梦视频3.0 720P文生视频](https://docs.volcengine.com/docs/85621/1792704?lang=zh)。先开通对应服务，并准备有调用权限的Access Key和Secret Key。本项目用英文冒号连接为 `AK:SK`，由签名工具拆开计算请求签名。这不是文本模型的Bearer API Key，不能直接混用。

| 配置 | 图片 | 视频 |
|---|---|---|
| provider | jimeng | jimeng |
| base_url | https://visual.volcengineapi.com | https://visual.volcengineapi.com |
| model（发送为req_key） | jimeng_t2i_v30 | jimeng_t2v_v30 |
| 课堂尺寸 | 1024*1024 | 1280*720（转换为16:9） |
| 时长 | 不适用 | 5秒，也可以设10秒 |

提交Action为 `CVSync2AsyncSubmitTask`，查询Action为 `CVSync2AsyncGetResult`，Version为 `2022-08-31`，签名Region为 `cn-north-1`、Service为 `cv`。代码自动拼接查询参数，不要在Base URL后添加聊天路径。

视频帧数为 `24 × 秒数 + 1`，仅允许121或241帧。第15章30秒策划脚本不等于本接口能一次生成30秒成片。先选择适合5秒呈现的镜头；提示词建议400字以内，不能超过800字。当前模型仅支持文生视频，方案中的 `reference_images` 必须为空。

### 16.3.5 理解响应与签名

提交、查询都必须先检查外层code等于10000，再读取data；失败时data可能为null。视频的in_queue、generating表示继续等待；done还需成功码与视频URL；not_found、expired则停止并报告错误。

视频URL有效期仅一小时，成功后立即下载到项目本地，后续使用本地素材地址。图片查询的req_json是JSON序列化后的字符串，用于要求返回URL。视频查询可以省略req_json；需要隐式标识时按官方aigc_meta定义扩展，不要删除已有标识。

签名第一轮HMAC直接使用原始Secret Key，再依次派生日期、区域、服务和request密钥，不能自行加前缀。下一节代码对齐[官方Python SDK签名实现](https://github.com/volcengine/volc-sdk-python/blob/main/volcengine/auth/SignerV4.py)。

### 16.4.1 先编写火山/即梦签名工具

创建 `api/app/services/volcengine.py`。先定义凭证错误类型，再实现 `parse_access_key_pair()`，将配置中的访问密钥对解析为 Access Key 与 Secret Key；随后实现签名所需的日期、规范请求和 `signed_json_headers()`。图片和视频都复用它，因此必须先完成。

```python
from datetime import UTC, datetime
import hashlib
import hmac
from urllib.parse import urlencode, urlparse


class VolcengineCredentialsError(RuntimeError):
    pass


def parse_access_key_pair(api_key: str | None) -> tuple[str, str]:
    """解析访问keypair；集中执行业务校验、状态变更与持久化，并返回可验证结果。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    if not api_key or ":" not in api_key:
        raise VolcengineCredentialsError(
            "Jimeng provider expects api_key in 'VOLC_ACCESS_KEY:VOLC_SECRET_KEY' format."
        )
    access_key, secret_key = api_key.split(":", 1)
    access_key = access_key.strip()
    secret_key = secret_key.strip()
    if not access_key or not secret_key:
        raise VolcengineCredentialsError(
            "Jimeng provider expects both Volcengine access key and secret key."
        )
    return access_key, secret_key


def signed_json_headers(
    *,
    access_key: str,
    secret_key: str,
    method: str,
    url: str,
    query: dict[str, str],
    body: bytes,
    region: str = "cn-north-1",
    service: str = "cv",
    request_time: datetime | None = None,
) -> dict[str, str]:
    """签名JSONheaders；集中执行业务校验、状态变更与持久化，并返回可验证结果。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    request_time = request_time or datetime.now(UTC)
    x_date = request_time.strftime("%Y%m%dT%H%M%SZ")
    short_date = request_time.strftime("%Y%m%d")
    parsed = urlparse(url)
    host = parsed.netloc
    canonical_uri = parsed.path or "/"
    canonical_query = urlencode(sorted(query.items()))
    payload_hash = hashlib.sha256(body).hexdigest()
    signed_headers = "content-type;host;x-content-sha256;x-date"
    canonical_headers = (
        "content-type:application/json\n"
        f"host:{host}\n"
        f"x-content-sha256:{payload_hash}\n"
        f"x-date:{x_date}\n"
    )
    canonical_request = "\n".join(
        [
            method.upper(),
            canonical_uri,
            canonical_query,
            canonical_headers,
            signed_headers,
            payload_hash,
        ]
    )
    credential_scope = f"{short_date}/{region}/{service}/request"
    string_to_sign = "\n".join(
        [
            "HMAC-SHA256",
            x_date,
            credential_scope,
            hashlib.sha256(canonical_request.encode("utf-8")).hexdigest(),
        ]
    )
    signature = _signing_signature(secret_key, short_date, region, service, string_to_sign)

    return {
        "Authorization": (
            "HMAC-SHA256 "
            f"Credential={access_key}/{credential_scope}, "
            f"SignedHeaders={signed_headers}, Signature={signature}"
        ),
        "Content-Type": "application/json",
        "Host": host,
        "X-Content-Sha256": payload_hash,
        "X-Date": x_date,
    }


def _signing_signature(
    secret_key: str,
    short_date: str,
    region: str,
    service: str,
    string_to_sign: str,
) -> str:
    """signingsignature，统一主流程中的格式、默认值和异常边界。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    key = _hmac(secret_key.encode("utf-8"), short_date)
    key = _hmac(key, region)
    key = _hmac(key, service)
    key = _hmac(key, "request")
    return hmac.new(key, string_to_sign.encode("utf-8"), hashlib.sha256).hexdigest()


def _hmac(key: bytes, message: str) -> bytes:
    """HMAC，统一主流程中的格式、默认值和异常边界。"""
    return hmac.new(key, message.encode("utf-8"), hashlib.sha256).digest()
```

验证时不需要联网：用单元测试或临时字符串检查“缺少密钥对会报配置错误”，而不是打印真实 Secret Key。

```python
def _post_jimeng_json(
    *,
    settings: Settings,
    action: str,
    payload: dict[str, Any],
    timeout: int,
) -> dict[str, Any]:
    """发送jimengJSON，统一主流程中的格式、默认值和异常边界。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    try:
        access_key, secret_key = parse_access_key_pair(settings.image_api_key)
    except VolcengineCredentialsError as exc:
        raise ImageGenerationNotConfiguredError(str(exc)) from exc

    base_url = settings.image_base_url or "https://visual.volcengineapi.com"
    query = {"Action": action, "Version": "2022-08-31"}
    body = json.dumps(payload, ensure_ascii=False, separators=(",", ":")).encode("utf-8")
    headers = signed_json_headers(
        access_key=access_key,
        secret_key=secret_key,
        method="POST",
        url=base_url,
        query=query,
        body=body,
    )
    try:
        with httpx.Client(timeout=timeout) as client:
            response = client.post(base_url, params=query, content=body, headers=headers)
            response.raise_for_status()
            data = response.json()
    except httpx.HTTPStatusError as exc:
        raise ImageGenerationError(_provider_error_detail(exc.response)) from exc
    except httpx.HTTPError as exc:
        raise ImageGenerationError(_http_error_detail("Jimeng image request failed", exc)) from exc

    code = data.get("code")
    if code != 10000:

def _extract_jimeng_task_id(data: dict[str, Any]) -> str:
```

## 16.5 编写视频生成服务

### 16.5.1 视频服务复用什么，又新增什么

创建 `api/app/services/video_generation.py`。开始部分与图片服务相同：配置校验、方案类型校验、提示词清洗、供应商适配、轮询和下载。不同之处是：视频只能读取 `VIDEO_SCRIPT`；`_video_workflow()` 还会整理参考图、字幕、配音和剪辑说明；返回结果包含建议时长和工作流元数据。

请注意第15章脚本的 `duration_seconds` 是创意建议，不保证供应商一定按每一个分镜逐帧实现，因此供应商返回视频后仍要人工审核。

```python

import uuid
import json
from typing import Any

import httpx

from app.core.config import API_DIR, Settings
from app.models import CreativePlan, CreativePlanType
from app.services.model_settings import get_runtime_settings
from app.services.volcengine import VolcengineCredentialsError, parse_access_key_pair, signed_json_headers


class VideoGenerationNotConfiguredError(RuntimeError):
    pass


class VideoGenerationError(RuntimeError):
    pass


GENERATED_VIDEOS_DIR = API_DIR / "uploads" / "generated-videos"


def is_video_generation_configured(settings: Settings | None = None) -> bool:
    """判断视频生成任务configured；集中执行业务校验、状态变更与持久化，并返回可验证结果。"""
    settings = settings or get_runtime_settings()

        settings.video_provider
        and settings.video_base_url
        and settings.video_api_key
        and settings.video_model

def generate_video_asset(
    creative_plan: CreativePlan,
    *,
    settings: Settings | None = None,
) -> dict[str, Any]:
    """生成视频素材；集中执行业务校验、状态变更与持久化，并返回可验证结果。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    settings = settings or get_runtime_settings()
    if not is_video_generation_configured(settings):
        raise VideoGenerationNotConfiguredError("Video generation provider is not configured.")
    if settings.video_provider != "jimeng":
        raise VideoGenerationNotConfiguredError(
            f"Unsupported video provider: {settings.video_provider}. "
            "This provider can be saved in settings, but its generation adapter is not implemented yet."
        )
    if creative_plan.type != CreativePlanType.VIDEO_SCRIPT:
        raise VideoGenerationError("Only video script plans can generate video assets.")

    # 视频生成保留 workflow 元数据，方便运营复核参考图、字幕和配音，不把结果做成只读黑盒。
    prompt = _sanitize_video_prompt(_video_prompt(creative_plan))
    workflow = _video_workflow(creative_plan)
    if settings.video_model != "jimeng_t2v_v30":
        raise VideoGenerationNotConfiguredError("本章视频模型必须为 jimeng_t2v_v30。")
    task_id = create_jimeng_video_task(prompt, settings, workflow=workflow)
    result = poll_jimeng_video_task(task_id, settings)
    video_url = _extract_jimeng_video_url(result)

    return {
        "provider": settings.video_provider,
        "model": settings.video_model,
        "size": settings.video_size,
        "duration": settings.video_duration,
        "prompt": prompt,
        "workflow": workflow,
        "task_id": task_id,
        "source_url": video_url,
        "url": public_path,
        "created_at": int(time.time()),
    }


def create_jimeng_video_task(
    prompt: str,
    settings: Settings,

    payload = {
        "req_key": settings.video_model,
        "prompt": prompt,
        "seed": -1,
        "frames": _duration_to_frames(settings.video_duration),
        "aspect_ratio": _aspect_ratio_from_size(settings.video_size),
    }
    reference_images = (workflow or {}).get("reference_images") or []
    if reference_images:
        raise VideoGenerationError("jimeng_t2v_v30 是文生视频模型，请清空 reference_images；图生视频需另接专用接口。")
    data = _post_jimeng_video_json(
        settings=settings,
        action="CVSync2AsyncSubmitTask",
        payload=payload,
        timeout=120,
    )
    task_id = _extract_jimeng_task_id(data)
    if not task_id:
        raise VideoGenerationError("Jimeng video response did not contain task_id.")
    return task_id


def poll_jimeng_video_task(task_id: str, settings: Settings) -> dict[str, Any]:

    max_attempts = max(settings.video_poll_max_attempts, 1)
    interval = max(settings.video_poll_interval_seconds, 1)
    payload = {"req_key": settings.video_model, "task_id": task_id}

    for _attempt in range(max_attempts):
        data = _post_jimeng_video_json(
            settings=settings,
            action="CVSync2AsyncGetResult",
            payload=payload,
            timeout=30,
        )
        status_value = _jimeng_status(data)
        if status_value in {"done", "succeeded", "success", ""} and _extract_jimeng_video_url(data):
            return data
        if status_value in {"failed", "expired", "not_found"}:
            raise VideoGenerationError(f"Jimeng video task ended with status: {status_value}")
        time.sleep(interval)

    raise VideoGenerationError("Jimeng video task timed out.")


def _post_jimeng_video_json(
    *,
    settings: Settings,
    action: str,
    payload: dict[str, Any],
    timeout: int,
) -> dict[str, Any]:
    """发送jimeng视频JSON，统一主流程中的格式、默认值和异常边界。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    try:

    except VolcengineCredentialsError as exc:
        raise VideoGenerationNotConfiguredError(str(exc)) from exc

    base_url = settings.video_base_url or "https://visual.volcengineapi.com"

    try:

    except httpx.HTTPStatusError as exc:
        raise VideoGenerationError(_provider_error_detail(exc.response)) from exc
    except httpx.HTTPError as exc:
        raise VideoGenerationError(_http_error_detail("Jimeng video request failed", exc)) from exc

    code = data.get("code")
    if code != 10000:
        raise VideoGenerationError(str(data)[:500])
    return data

def _duration_to_frames(duration: int) -> int:

    if duration not in {5, 10}:
        raise VideoGenerationError("即梦720P文生视频仅支持5秒或10秒。")
    return 24 * duration + 1


def _aspect_ratio_from_size(size: str) -> str:
    """aspect比率fromsize，统一主流程中的格式、默认值和异常边界。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    normalized = size.replace("*", "x").lower()
    parts = normalized.split("x", 1)
    if len(parts) != 2:
        return "16:9"
    try:
        width = int(parts[0])
        height = int(parts[1])
    except ValueError:
        return "16:9"
    if width <= 0 or height <= 0:
        return "16:9"
    ratio = width / height
    candidates = {
        "16:9": 16 / 9,
        "4:3": 4 / 3,
        "1:1": 1,
        "3:4": 3 / 4,
        "9:16": 9 / 16,
        "21:9": 21 / 9,
    }
    return min(candidates, key=lambda item: abs(candidates[item] - ratio))


def _video_prompt(creative_plan: CreativePlan) -> str:

    content = creative_plan.content or {}
    prompt = content.get("video_prompt")
    if isinstance(prompt, str) and prompt.strip():
        return prompt.strip()

    scene_lines: list[str] = []
    scenes = content.get("scenes", [])
    if isinstance(scenes, list):
        for scene in scenes:
            if not isinstance(scene, dict):
                continue
            visual = scene.get("visual", "")
            if isinstance(visual, str) and visual.strip():
                scene_lines.append(visual.strip())

    parts = [
        f"电商短视频，脚本标题：{creative_plan.title}",
        f"核心角度：{content.get('angle', '')}",
        f"开头钩子：{content.get('hook', '')}",
        "镜头画面：" + "；".join(scene_lines),
        f"转化引导：{content.get('cta', '')}",
        "商业广告质感，画面干净，产品主体清晰，适合电商信息流投放。",
    ]
    workflow_lines = _workflow_prompt_lines(content)

        parts.insert(-1, workflow_lines)
    return "\n".join(part for part in parts if part.strip())
```

## 16.6 在第17章接入任务路由

媒体服务本身只负责“给定一个正确的创意方案，生成并返回素材字典”。不能在这里直接让 HTTP 接口等待几十秒甚至更久。下一章会在既有 `products.py` 中增加图片和视频生成端点：它们校验商品和方案归属，创建 `GenerationJob`，返回 `202 Accepted` 和本地任务 ID，再由后台执行服务。

因此本章结束时，能独立验证提示词、签名、供应商响应解析、下载和素材入库；完整的“提交接口后后台跑起来”的链路，要等第17章的任务状态机、调度、取消和重试一起完成。

### 16.7.2 用 Swagger 做人工验收与素材审核

继续使用15.8.2中的“低糖燕麦饼干”、实际商品 ID，以及已经生成的主图方案和视频脚本。本节默认后端正在运行、Swagger 已授权，不再重复启动服务、登录、创建店铺商品或生成文字方案。

先明确执行时机：**第16章现在可以完成图片/视频配置检查与文字方案人工筛选；真实媒体生成和生成后的素材审核，需要完成第17章任务路由与执行环境后再继续。** 第16章只加入媒体服务文件，不会自动把旧的生成占位接口变成可用接口。已经有真实生成素材的同学，可以直接执行后面的素材审核步骤。

| 执行阶段 | 本节操作 |
|---|---|
| 第16章现在执行 | 第一步至第三步：确认媒体配置、定位方案、审核并选用方案 |
| 完成第17章后执行 | 第四步至第九步：提交生成、查询任务、检查真实文件、审核素材、验证保存 |
| 当前服务层的自动化验证 | 运行16.8.1对应的媒体与素材测试，不以生成接口返回202作为本章立即可达的条件 |

**第一步：只检查本章新增的图片、视频配置。**

在 `GET /api/v1/model-settings` 中点击 **Try it out → Execute**，重点检查 `image` 和 `video` 两组数据，而不是再次测试已通过的文本模型：

| 配置字段 | 检查内容 |
|---|---|
| `provider` | 图片、视频均为 `jimeng`，完整设置见16.3.4 |

| `poll_interval_seconds`、`poll_max_attempts` | 使用前面配置的合理轮询间隔及次数，不能设成0 |

如果前面只配置过文本模型，需要通过 `PATCH /api/v1/model-settings` 补充相应的 `image` 或 `video` 配置；如果两类媒体配置已保存且正确，不必再次提交。请求体仅提交要更新的目标，例如下列结构中的占位文字必须替换为实际配置后才能执行：

```json
{
  "image": {
    "provider": "jimeng",
    "base_url": "替换为图片服务Base URL",
    "api_key": "替换为图片服务密钥",
    "model": "替换为实际图片模型",
    "size": "替换为模型支持的尺寸"
  }
}
```

配置视频时使用 `video` 对象，按对应模型填写 `duration` 等字段；不是把 `image` 的模型名和地址原样复制一遍。视频密钥也不要默认与文本或图片密钥相同。保存成功预期200，再次GET确认生效。已有密钥无需更新时，省略 `api_key` 字段。

第14章配套的 `POST /api/v1/model-settings/test` 目前只实现了 `target: "text"`；本章配套代码未补充它的媒体测试实现，因此不要将 `target: "image"` 或 `"video"` 返回501当作供应商配置失败。媒体调用是否成功，要在第17章接入后通过真实生成任务验证。

**第二步：找到本次要使用的两条方案。**

调用 `GET /api/v1/products/{product_id}`，填写第15章保存的实际商品 ID。预期200，在 `creative_plans` 数组中选出：

- 一条 `type: "main_image"` 的主图方案，记下其 `id`，下文称为“主图方案 ID”。
- 一条 `type: "video_script"` 的视频脚本，记下其 `id`，下文称为“视频脚本 ID”。

这两个 ID 都来自方案记录，不是商品 ID、任务 ID 或素材 ID。后续接口同时出现 `product_id` 和 `creative_plan_id` 时，必须分别填写商品编号及当前方案编号。

检查主图方案的 `content.image_prompt`、标题和布局是否完整；检查视频脚本的 `content.video_prompt`、`scenes`、`voiceover` 等内容是否完整。不要把主图方案编号填进视频生成接口。

**第三步：人工审核文字方案，并标记选用。**

先阅读模型输出，再决定是否用于生成。围绕“低糖燕麦饼干”重点检查：

| 检查项 | 本案例如何判断 |
|---|---|
| 商品一致性 | 商品名称、燕麦口味、独立小包装、12包装等描述是否与课堂商品资料一致 |
| 宣传内容 | 是否把“低糖”擅自改成“无糖”，或编造减肥、治疗效果、认证和销量 |
| 主图表达 | 主体清楚、包装数量合理、文字不过密，提示词不依赖当前没有提供的真实包装参考图 |
| 视频逻辑 | 镜头顺序、画面和配音相互对应，结尾行动引导清楚，避免虚构已发生的真实消费反馈 |
| 时长边界 | 第15章脚本的策划时长与视频模型单次生成时长不是一回事；短片结果不等于整份脚本已完整制作 |

本案例使用模拟商品资料，审核通过只表示适合课堂继续生成，不代表已经满足真实商品发布要求。如果需要修改 `content`，先从商品详情复制该方案的**完整 content 对象**，只改其中需要调整的字段，再通过下一条接口提交。现有接口会整体替换 `content`，只提交 `{"content":{"image_prompt":"..."}}` 会丢失其他方案字段。

审核通过后，展开 `PATCH /api/v1/products/{product_id}/creative-plans/{creative_plan_id}`，填写商品 ID 和主图方案 ID，请求体填写：

```json
{
  "status": "selected"
}
```

预期200，检查响应 `id` 为本次方案 ID，`status: "selected"`，原有 `content` 仍完整。然后对视频脚本 ID 执行同样的操作。

不选用的方案可以保留 `draft`，或通过同一接口改为 `archived`。方案状态只有 `draft`、`selected`、`archived`，不要填 `approved` 或中文“通过”。`selected` 是人工筛选记录，当前生成路由没有把它实现为强制审批闸门，因此录课时要主动完成审核步骤。

**本章停点：到这里已完成配置检查和方案筛选。下面的步骤请在完成第17章任务接入后执行。**

**第四步：提交主图生成任务。**

完成第17章的任务路由、调度与对应执行环境后，展开：

`POST /api/v1/products/{product_id}/creative-plans/{creative_plan_id}/images/generate`

点击 **Try it out**，填写当前商品 ID 和第三步选中的主图方案 ID，直接 **Execute**，无需请求体。模型会使用已保存的 `content.image_prompt`，不需要把提示词再粘贴进 Swagger。

预期202，返回的是本地任务对象。记录：

| 响应字段 | 应如何检查 |
|---|---|
| `id` | 记作图片任务 ID，用于查找本地任务；不是供应商 task_id |
| `product_id`、`creative_plan_id` | 与刚才提交的商品和主图方案一致 |
| `kind` | `main_image_asset` |
| `status` | 初始通常为 `pending`；后续查询可能已变为 `running` 或终态 |
| `result` | 刚提交时可以为空，不能据此认定生成失败 |

202只表示任务已受理。此时不要反复点击生成接口来“刷新进度”，每次提交都可能新增任务并产生供应商费用。

**第五步：查询图片任务并打开真实文件。**

继续使用已有的 `GET /api/v1/products/{product_id}` 查询商品详情，在 `generation_jobs` 中按第四步记录的任务 ID 查找，不要仅凭列表第一条判断。等待几秒后可再次点击该GET接口的 **Execute**。

- `pending`：等待执行；如果一直不变化，检查第17章选择的执行模式及任务调度环境。
- `running`：正在请求供应商、轮询或下载，继续等待。
- `succeeded`：再检查任务结果和素材记录，不能只看状态。
- `failed`：查看该任务的 `error`、`events`，根据实际错误排查模型、权限、参数、网络或下载问题。
- `cancelled`：任务已取消，不按生成成功验收。

成功后，在商品详情的 `generated_assets` 中找到对应 `creative_plan_id`、`generation_job_id` 和 `asset_type: "image"` 的记录。检查 `url` 为项目保存的素材地址，`model` 和元数据与本次生成匹配，审核状态初始通常为“待评估”。

复制响应里的实际 `url`。如果它以 `/uploads/` 开头，在浏览器地址栏前面加上后端地址 `http://127.0.0.1:8000` 后打开。例如 `/uploads/generated/某文件.png` 对应后端的同路径地址；必须使用响应中的真实文件名，不能照抄这个示意文件名。能正常显示图片，才证明下载和静态文件访问链路可用。

同时检查该方案 `content.generated_images` 中的素材条目。后面审核接口用它的原始 `url` 定位素材；在浏览器打开时拼接的完整地址，不一定是数据库中存储的原始值。

**第六步：提交视频任务并检查播放。**

展开：

`POST /api/v1/products/{product_id}/creative-plans/{creative_plan_id}/videos/generate`

填写当前商品 ID 和第三步选中的**视频脚本 ID**，无需请求体，执行一次。预期202，记录新任务 `id`，检查 `kind: "video_asset"`。然后按第五步同样的方法从商品详情查询任务状态。

成功后，在 `generated_assets` 中查找该视频脚本及任务对应的 `asset_type: "video"` 记录，使用实际 `url` 打开文件，检查是否可以播放、画面是否连贯、商品与场景是否一致。

本章固定使用 `jimeng_t2v_v30` 文生视频，`reference_images` 必须为空。若已有参考图，先保留完整content的其他字段，将reference_images改为空数组后保存；不要更换为图生视频模型。

视频文件时长受供应商模型及 `video.duration` 配置约束，不能只因为第15章脚本写了30秒，就断言本次一定返回30秒成片。字幕、配音与剪辑要求可能只是提示词或工作流信息，是否真正出现在视频里要以播放结果为准。

**第七步：审核主图素材并保存评价。**

打开生成的主图，检查包装和饼干是否变形、商品数量是否合理、中文是否清晰、是否出现未要求的品牌或虚构宣传。合格后展开：

`PATCH /api/v1/products/{product_id}/creative-plans/{creative_plan_id}/assets`

填写商品 ID 和对应的主图方案 ID。下面 `url` 是占位示例，必须替换为第五步从素材记录复制的**原始 url**，其他字段可作为课堂评价示例：

```json
{
  "url": "/uploads/generated/替换为实际图片文件名.png",
  "asset_type": "image",
  "status": "通过",
  "rating": 4,
  "tags": [
    "低糖燕麦饼干",
    "主体清晰",
    "独立包装"
  ],
  "note": "课堂人工审核：商品主体与方案一致，画面清楚，可进入后续小范围效果测试。",
  "asset_version": 1,
  "usage_contexts": [
    "商品主图",
    "课堂素材对比"
  ]
}
```

执行后预期200，响应是更新后的创意方案，不是单独的素材对象。检查 `content.generated_images` 中对应URL的 `status`、`rating` 和 `note` 是否更新。

如果画面不合格，应根据实际情况填写“弃用”或“复测”，不要为了完成验收一律写“通过”。`rating` 是1～5的评分；`asset_version` 是素材版本标记，不是重新生成次数，修改它不会触发新模型任务。

**第八步：审核视频素材。**

调用与第七步相同的PATCH接口，但路径中的 `creative_plan_id` 改为视频脚本 ID，`url` 改为实际视频素材原始URL，`asset_type` 改为 `video`。下面演示“需要复测”的评价，可按真实播放情况调整：

```json
{
  "url": "/uploads/generated/替换为实际视频文件名.mp4",
  "asset_type": "video",
  "status": "复测",
  "rating": 3,
  "tags": [
    "低糖燕麦饼干",
    "视频初稿"
  ],
  "note": "课堂审核示例：需继续检查包装文字与镜头连贯性，调整提示词后再比较效果。",
  "asset_version": 1,
  "usage_contexts": [
    "短视频素材测试"
  ]
}
```

预期200，检查响应 `content.generated_videos` 中对应条目的评价。素材审核状态只接受“待评估”“通过”“弃用”“复测”，与第三步的方案状态不是同一套字段值。

“复测”只保存审核意见，不会自动重新生成视频；“通过”也不会自动发布或投放。需要生成新版本时，应调整完整方案后再按任务流程提交，并注意真实调用费用。

**第九步：重新查询，确认两处审核记录一致。**

再次执行 `GET /api/v1/products/{product_id}`，按刚才的URL核对：

1. `creative_plans` 中对应方案的 `content.generated_images` 或 `content.generated_videos` 已保存审核状态、评分和备注。
2. `generated_assets` 中相同URL的素材记录也保存了相同的审核字段。
3. 在新浏览器标签页打开素材地址仍可访问，证明审核没有破坏文件地址。

如果方案内容里有素材，但素材库没有对应记录，可以调用已有的 `POST /api/v1/products/{product_id}/assets/sync`：只填写商品 ID，无需请求体。预期200，返回 `{"created": 数量}`，表示本次新增的素材库记录数。再次同步且没有新增素材时应为0。这个接口只同步已有素材信息，不调用供应商、不生成或下载媒体文件。

**异常结果对照。**

| 现象 | 本节应如何判断 |
|---|---|
| 生成接口返回501 | 先确认是否完成第17章路由替换；第16章只有媒体服务时属于阶段边界 |
| 生成接口返回400且提示方案类型错误 | 检查主图方案和视频脚本 ID 是否填反 |
| 素材审核返回404 | 检查商品/方案归属、素材是否已生成，以及 `url` 是否与方案中保存的原始值完全一致 |
| 素材审核返回422 | 检查 `asset_type`、中文审核状态、评分范围，以及必填URL |
| 任务成功但文件打不开 | 检查是否使用8000端口、实际URL是否正确、下载文件和 `uploads` 静态目录是否存在 |
| 更新方案后提示词或镜头不见了 | 检查是否只提交了一小部分 `content`，导致完整对象被覆盖 |
| 任务失败 | 依据该任务的错误和事件排查，不要用手工填一个URL冒充生成成功 |

本节最终验收的是“真实文件可访问、人工意见可保存、方案与素材库记录一致”。只有文字方案、202响应或一条URL字符串，都不能单独代表媒体生成与审核闭环已经完成。

### 16.7.3 本章小结

第16章完成了“文字创意方案 → 可下载媒体文件 → 可管理素材记录”的媒体服务层。第17章将为它补上可靠的后台任务机制，使耗时过程能被查询、取消、重试并在失败时留下清晰事件。

# 17 — 后台生成任务与可靠执行

图片或视频生成可能持续几十秒甚至更久。若 FastAPI 接口一直等待供应商完成，浏览器断开、Web 进程重启或多人同时提交时，用户将不知道结果在哪里。本章将耗时工作改成可追踪的本地任务：接口只创建任务记录并返回，后台再执行；无论成功、失败、重试还是取消，用户都能查询同一个任务 ID。

> **本章完成后能得到什么？** 一个 `GenerationJob` 会经历 pending、running、succeeded、failed 或 cancelled 状态，并持续留下事件。开发环境可用 FastAPI BackgroundTasks 执行；Redis/Celery 环境可由 Worker 消费相同的任务 ID。

## 17.1 先理解状态机和事件

```text
接口校验商品与创意方案
        │
        ▼
enqueue_generation_job()：pending + queued 事件
        │
        ├─ inline：BackgroundTasks 调用 run_generation_job()
        └─ celery：Worker 消费 generation.run_generation_job
                 │
                 ▼
             running + started 事件
                 │
        ┌────────┴─────────┐
        ▼                  ▼
第16章媒体服务成功       异常、超时或供应商失败
        │                  │
        ▼                  ▼
succeeded + 素材记录    pending + retry_scheduled，或 failed
```

| 状态 | 含义 | 用户应做什么 |
|---|---|---|
| `pending` | 已入队，等待执行或等待下一次重试 | 查询进度，不重复提交 |
| `running` | Worker 已开始处理 | 等待结果；必要时请求取消 |
| `succeeded` | 文件下载并保存为素材 | 人工审核素材 |
| `failed` | 已到达重试上限或不可恢复失败 | 查看错误摘要，修正后重试 |
| `cancelled` | 本项目不再继续执行 | 必要时创建新任务 |

状态回答“现在是什么”；事件回答“经历过什么”。`queued`、`started`、`retry_scheduled`、`succeeded`、`failed`、`cancelled`、`timeout_checked` 都是排查链路的重要事实。事件只记录安全摘要、状态与本地结果 URL，不保存 API Key 或完整供应商响应。

## 17.2 任务服务的职责边界

`generation_jobs.py` 不负责登录、商品归属校验或解析 HTTP 请求，这些仍在路由中完成；它也不在路由线程里做图片生成。它只负责创建记录、状态转换、调用第16章服务、保存生成素材、安排重试和写入事件。

并发下的第一道保护是：`run_generation_job()` 只处理仍为 `pending` 的任务。若任务已取消、已成功或被其他 Worker 抢先标为 running，函数直接返回，避免同一条本地任务被重复执行。它不能绝对保证外部供应商永远不会收到重复请求，因此涉及费用的生成仍需要任务记录和人工审核。

### 17.4.1 创建 `generation_jobs.py`

创建 `api/app/services/generation_jobs.py`。阅读和编写时按函数分四组进行：

1. `enqueue_generation_job()`、`record_generation_job_event()`：创建任务和第一条事件；
2. `run_generation_job()`、`_mark_running()`、`_generate_asset()`：执行一次任务，调用第16章图片或视频服务并保存素材；
3. `_mark_failed_or_retry()`、`retry_generation_job_record()`、`cancel_generation_job_record()`：处理可恢复或人工发起的状态变化；
4. `mark_stale_running_generation_jobs()`、`dispatch_generation_job()`、`process_next_generation_job()`：处理超时和选择 inline / Celery 执行方式。

```python
from datetime import UTC, datetime, timedelta

from sqlalchemy import select
from sqlalchemy.orm import Session

from app.core.config import get_settings
from app.db.session import SessionLocal
from app.models import CreativePlan, GenerationJob, GenerationJobEvent, GenerationJobKind, GenerationJobStatus
from app.services.generated_assets import create_generated_asset
from app.services.image_generation import generate_main_image_asset
from app.services.video_generation import generate_video_asset


DEFAULT_MAX_ATTEMPTS = 3
DEFAULT_RUNNING_TIMEOUT_MINUTES = 30


def enqueue_generation_job(
    db: Session,
    product_id: int,
    creative_plan_id: int,
    kind: GenerationJobKind,
    max_attempts: int = DEFAULT_MAX_ATTEMPTS,
) -> GenerationJob:
    # 生成图片/视频可能耗时较长，API 只负责落任务记录，实际执行交给后台队列并保留可追踪状态。
    """enqueue生成任务任务；集中执行业务校验、状态变更与持久化，并返回可验证结果。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    job = GenerationJob(

        creative_plan_id=creative_plan_id,
        kind=kind,

        attempts=0,
        max_attempts=max_attempts,

    )
    db.add(job)
    record_generation_job_event(

        message="生成任务已入队。",
        payload={"kind": kind.value, "max_attempts": max_attempts},
    )

def retry_generation_job_record(job: GenerationJob) -> None:
    # 重试时清空上一次执行痕迹，但保留同一任务 ID，前端和审计日志可以串起完整生命周期。
    """重试生成任务任务记录；集中执行业务校验、状态变更与持久化，并返回可验证结果。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    job.status = GenerationJobStatus.PENDING
    job.result = {}
    job.error = None
    job.locked_at = None
    job.locked_by = None
    job.started_at = None
    job.finished_at = None
    job.next_run_at = datetime.now(UTC)
    record_generation_job_event(
        job,
        "retry_requested",
        message="用户请求重试生成任务。",
        payload={"next_run_at": job.next_run_at.isoformat()},
    )


def cancel_generation_job_record(job: GenerationJob, *, reason: str | None = None) -> bool:
    # 只允许取消尚未结束的任务；已成功或失败的记录是历史事实，不在这里做状态回滚。
    """取消生成任务任务记录；集中执行业务校验、状态变更与持久化，并返回可验证结果。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    if job.status not in {GenerationJobStatus.PENDING, GenerationJobStatus.RUNNING}:
        return False
    job.status = GenerationJobStatus.CANCELLED
    job.error = reason or "任务已取消。"
    job.locked_at = None
    job.locked_by = None
    job.next_run_at = None
    job.finished_at = datetime.now(UTC)
    record_generation_job_event(
        job,
        "cancelled",
        message=job.error,
        payload={"reason": reason or "user_cancelled"},
    )
    return True


def mark_stale_running_generation_jobs(
    db: Session,
    *,
    timeout_minutes: int = DEFAULT_RUNNING_TIMEOUT_MINUTES,
    now: datetime | None = None,
) -> int:
    """标记超时running生成任务jobs；集中执行业务校验、状态变更与持久化，并返回可验证结果。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    current_time = now or datetime.now(UTC)
    deadline = current_time - timedelta(minutes=timeout_minutes)
    jobs = db.scalars(
        select(GenerationJob).where(
            GenerationJob.status == GenerationJobStatus.RUNNING,
            GenerationJob.started_at.is_not(None),
            GenerationJob.started_at <= deadline,
        )
    ).all()
    for job in jobs:
        # 超时任务视为 worker 执行链路中断：释放锁并按重试策略重新排队，避免长期卡在 running。
        _mark_failed_or_retry(job, RuntimeError(f"生成任务运行超过 {timeout_minutes} 分钟，已按超时处理。"))
        job.locked_at = None
        job.locked_by = None
        job.finished_at = current_time
        record_generation_job_event(
            job,
            "timeout_checked",
            message="调度器已处理运行超时任务。",
            payload={"timeout_minutes": timeout_minutes},
        )
    db.commit()
    return len(jobs)


def dispatch_generation_job(job_id: int, background_tasks: object | None = None) -> None:
    """调度生成任务；集中执行业务校验、状态变更与持久化，并返回可验证结果。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    settings = get_settings()
    if settings.task_queue_backend == "celery":
        # 生产环境优先走 Celery，避免长耗时生成阻塞 Web 进程，也便于后续横向扩 worker。
        from app.worker.tasks import run_generation_job_task

        run_generation_job_task.delay(job_id)
        return

    if background_tasks is not None and hasattr(background_tasks, "add_task"):
        # 本地和轻量部署可使用 FastAPI background task，保持原型部署简单。
        background_tasks.add_task(run_generation_job, job_id)
        return

    run_generation_job(job_id)


def process_next_generation_job(worker_id: str = "fastapi-background") -> int | None:
    """处理下次生成任务任务；集中执行业务校验、状态变更与持久化，并返回可验证结果。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    now = datetime.now(UTC)
    with SessionLocal() as db:
        # 单次只取最早可执行任务，便于用定时器或单 worker 轮询时控制并发和重试节奏。
        statement = (
            select(GenerationJob)
            .where(
                GenerationJob.status == GenerationJobStatus.PENDING,
                (GenerationJob.next_run_at.is_(None)) | (GenerationJob.next_run_at <= now),
            )
            .order_by(GenerationJob.created_at.asc())
            .limit(1)
        )
        job = db.scalars(statement).first()
        if job is None:
            return None
        job_id = job.id

    run_generation_job(job_id, worker_id=worker_id)
    return job_id


def run_generation_job(job_id: int, worker_id: str = "fastapi-background") -> None:
    """执行生成任务任务；集中执行业务校验、状态变更与持久化，并返回可验证结果。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    with SessionLocal() as db:
        # MySQL 行锁让 API 后台、调度器和 Worker 的重复消息只能有一个开始执行。
        job = db.get(GenerationJob, job_id, with_for_update=True)
        # 任务可能被用户取消、重试或其他 worker 抢先处理；非 pending 时直接退出，避免重复生成素材。
        if job is None or job.status != GenerationJobStatus.PENDING:
            return

        # SQLite/MySQL 驱动可能返回无时区值，数据库时间按 UTC 解释。
        due_at = job.next_run_at
        if due_at is not None and due_at.tzinfo is None:
            due_at = due_at.replace(tzinfo=UTC)
        if due_at is not None and due_at > datetime.now(UTC):
            return

        _mark_running(job, worker_id)
        db.commit()

        try:
            creative_plan = db.scalars(
                select(CreativePlan).where(CreativePlan.id == job.creative_plan_id)
            ).first()
            if creative_plan is None:
                raise RuntimeError("Creative plan not found.")

            asset = _generate_asset(db, job, creative_plan)
            job.result = asset
            job.status = GenerationJobStatus.SUCCEEDED
            job.error = None
            job.next_run_at = None
            record_generation_job_event(
                job,
                "succeeded",
                message="生成任务执行成功。",
                payload={"result_url": asset.get("url"), "attempts": job.attempts},
                worker_id=worker_id,
            )
        except Exception as exc:
            _mark_failed_or_retry(job, exc)
        finally:
            job.locked_at = None
            job.locked_by = None
            job.finished_at = datetime.now(UTC)
            db.commit()


def _mark_running(job: GenerationJob, worker_id: str) -> None:
    """标记running，统一主流程中的格式、默认值和异常边界。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    job.status = GenerationJobStatus.RUNNING
    job.attempts += 1
    job.started_at = datetime.now(UTC)
    job.finished_at = None
    job.locked_at = job.started_at
    job.locked_by = worker_id
    record_generation_job_event(
        job,
        "started",
        message="worker 已开始执行生成任务。",
        payload={"attempts": job.attempts},
        worker_id=worker_id,
    )


def _generate_asset(db: Session, job: GenerationJob, creative_plan: CreativePlan) -> dict:
    """生成素材，统一主流程中的格式、默认值和异常边界。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    if job.kind == GenerationJobKind.MAIN_IMAGE_ASSET:
        asset = generate_main_image_asset(creative_plan)
        _append_generated_asset(creative_plan, "generated_images", asset)
        create_generated_asset(db, creative_plan, "image", asset, job.id)
        return asset
    if job.kind == GenerationJobKind.VIDEO_ASSET:
        asset = generate_video_asset(creative_plan)
        _append_generated_asset(creative_plan, "generated_videos", asset)
        create_generated_asset(db, creative_plan, "video", asset, job.id)
        return asset
    raise RuntimeError(f"Unsupported generation job kind: {job.kind}")


def _mark_failed_or_retry(job: GenerationJob, exc: Exception) -> None:
    """标记失败or重试，统一主流程中的格式、默认值和异常边界。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    job.error = str(exc)[:2000]
    if job.attempts < job.max_attempts:
        # 外部生成供应商偶发超时较常见，采用短退避重试；超过上限后保留失败状态等待人工处理。
        job.status = GenerationJobStatus.PENDING
        job.next_run_at = datetime.now(UTC) + timedelta(minutes=min(job.attempts * 2, 10))
        record_generation_job_event(
            job,
            "retry_scheduled",
            message=job.error,
            payload={"attempts": job.attempts, "next_run_at": job.next_run_at.isoformat()},
        )
        return
    job.status = GenerationJobStatus.FAILED
    job.next_run_at = None
    record_generation_job_event(
        job,
        "failed",
        message=job.error,
        payload={"attempts": job.attempts},
    )


def _append_generated_asset(creative_plan: CreativePlan, key: str, asset: dict) -> None:
    """追加生成素材，统一主流程中的格式、默认值和异常边界。"""
    content = dict(creative_plan.content or {})
    existing = content.get(key, [])
    if not isinstance(existing, list):
        existing = []
    # 最新素材放在最前面，详情页展示和运营复核时优先看到最近一次生成结果。
    content[key] = [asset, *existing]
    creative_plan.content = content


def record_generation_job_event(
    job: GenerationJob,
    event_type: str,
    *,
    message: str | None = None,
    payload: dict | None = None,
    worker_id: str | None = None,
) -> GenerationJobEvent:
    # 事件日志用于排查任务生命周期，只记录状态和安全摘要，不保存模型 API key 或完整外部响应。
    """记录生成任务事件；集中执行业务校验、状态变更与持久化，并返回可验证结果。"""
    # 按“输入归一化 → 业务校验 → 状态或持久化”推进，异常不得留下半完成结果。
    event = GenerationJobEvent(
        event_type=event_type,
        status=job.status,
        message=message,
        payload=payload or {},
        worker_id=worker_id,
    )
    job.events.append(event)
    return event
```

### 17.4.2 为什么重试要保留同一个任务 ID

用户点击“重试”时，`retry_generation_job_record()` 清理错误、锁和完成时间，但不会新建一条任务。这样同一个 `GenerationJob.id` 可以串起第一次失败、后续重试和最终结果；审计、页面和事件列表不必猜测多条记录是否属于同一次业务请求。

失败后自动重试使用短退避：第 `attempts` 次失败会把 `next_run_at` 推迟一小段时间。超过 `max_attempts` 才真正变为 `failed`。超时扫描同样走这条规则：运行太久的任务会释放锁并重试或失败，避免永久卡在 `running`。

### 17.5.4 替换失败任务重试接口

pending/running任务只返回原记录，不重复投递；只有failed任务可以清理执行状态并用同一ID重新调度，历史尝试次数与事件保留。

```python
@router.post(
    "/{product_id}/generation-jobs/{job_id}/retry",
    response_model=GenerationJobRead,
    status_code=status.HTTP_202_ACCEPTED,
)
def retry_generation_job(
    product_id: int,
    job_id: int,
    background_tasks: BackgroundTasks,
    db: SessionDep,
    _current_user: Annotated[User, Depends(require_edit_permission)],

    """处理重试生成任务任务接口；完成身份、Workspace、资源归属和输入校验后返回结构化结果。"""
    # 先完成认证、Workspace 与资源归属校验，再进入会产生副作用的服务调用。
    get_product_or_404(db, product_id)
    job = db.get(GenerationJob, job_id)
    if job is None or job.product_id != product_id:
        raise HTTPException(status_code=status.HTTP_404_NOT_FOUND, detail="Generation job not found")
    if job.status in {GenerationJobStatus.PENDING, GenerationJobStatus.RUNNING}:
        # 已在队列或执行中的任务保持幂等返回，避免用户重复点击造成多条生成请求。
        return job
    if job.status != GenerationJobStatus.FAILED:
        raise HTTPException(status_code=status.HTTP_400_BAD_REQUEST, detail="Only failed jobs can be retried")

    retry_generation_job_record(job)
    db.commit()
    db.refresh(job)
    dispatch_generation_job(job.id, background_tasks)
    return job
```

### 17.6.3 编写到期任务调度器

`retry_scheduled` 只表示已经把重试时间写入数据库。还需要有进程不断检查这张表，才能在到期后再次执行。本章新增 `api/app/worker/generation_scheduler.py`，每5秒扫描一次，每轮最多处理20条到期的pending任务：

```python
"""扫描已到期的媒体任务；API、Worker 与调度进程使用同一份 api/.env。"""
import logging
import time
from datetime import UTC, datetime

from sqlalchemy import select

from app.db.session import SessionLocal
from app.models import GenerationJob, GenerationJobStatus
from app.services.generation_jobs import dispatch_generation_job

logger = logging.getLogger(__name__)
SCAN_INTERVAL_SECONDS = 5
BATCH_SIZE = 20


def dispatch_due_generation_jobs() -> int:
    """重新投递到期的 pending 任务，包括失败后等待重试和漏投递任务。"""
    now = datetime.now(UTC)
    with SessionLocal() as db:
        job_ids = list(db.scalars(
            select(GenerationJob.id)
            .where(
                GenerationJob.status == GenerationJobStatus.PENDING,
                (GenerationJob.next_run_at.is_(None)) | (GenerationJob.next_run_at <= now),
            )
            .order_by(GenerationJob.created_at.asc(), GenerationJob.id.asc())
            .limit(BATCH_SIZE)
        ))

    dispatched = 0
    for job_id in job_ids:
        try:
            # celery 模式投递消息；inline 模式在当前调度进程内执行。
            # 执行服务仍会在行锁内检查状态和到期时间，重复消息不会重复启动。
            dispatch_generation_job(job_id)
            dispatched += 1
        except Exception as exc:
            # 不打印可能包含连接密码的完整异常；保留 pending，下一轮再投递。
            logger.warning("任务 %s 调度失败，异常类型：%s", job_id, type(exc).__name__)
    return dispatched


def main() -> None:
    logging.basicConfig(level=logging.INFO, format="%(asctime)s %(levelname)s %(message)s")
    logger.info("媒体任务调度器启动：每 %s 秒扫描一次到期任务。", SCAN_INTERVAL_SECONDS)
    try:
        while True:
            try:
                count = dispatch_due_generation_jobs()
                if count:
                    logger.info("本轮处理 %s 条到期任务。", count)
            except Exception as exc:
                logger.warning("扫描失败，异常类型：%s；下一轮继续。", type(exc).__name__)
            time.sleep(SCAN_INTERVAL_SECONDS)
    except KeyboardInterrupt:
        logger.info("媒体任务调度器已停止。")


if __name__ == "__main__":
    main()
```

它与Worker分工不同：调度器负责发现到期任务；Celery模式下Worker才负责生成。inline模式没有独立Worker，调度器通过同一个服务在自身进程里执行到期任务，执行耗时会延长下一轮扫描间隔。

调度器可能与初次提交、队列重复投递同时发现相同任务，所以17.4的执行入口用MySQL行锁检查pending状态，再提交running状态，并检查 `next_run_at` 不得早于到期时间。课堂只启动一个调度器；Celery仍按单进程Worker演示。此机制避免同一等待状态被重复启动，不等于供应商侧具备恰好一次语义。

扫描器会处理首次投递失败而留在数据库中的pending记录，也会处理失败后的到期重试记录。它不会自动接管running任务；API/Worker意外退出后的超时回收需要另外启用17.4已有的维护函数，并在后续运行维护章节完善。本章不要把已保存的任务记录描述为自动恢复所有故障。

## 17.7 运行前环境检查 

| 检查项 | 为什么必须检查 |
|---|---|
| API、MySQL、Redis 地址 | Windows 本机、Docker、WSL2 的 `127.0.0.1` 并不代表同一服务 |
| API 与 Worker 的 `uploads` 目录 | Worker 下载到另一个文件系统时，数据库虽然成功，浏览器却打不开素材 |
| `TASK_QUEUE_BACKEND` | 本地可先使用 `inline`；没有 Redis 时不要切换到 `celery` |
| Redis 与 Celery 依赖 | 只有安装依赖、Redis 可访问且 Worker 已启动时，`.delay()` 才会被消费 |

本地开发可优先使用 inline：响应返回后由 BackgroundTasks 执行，不会阻塞 HTTP。它不具备进程重启后的恢复能力，适合学习和轻量演示。使用 Celery 时，先启动 Redis，再启动 Worker，最后启动 API；消息只传任务 ID，Worker 再通过数据库加载商品、方案和任务。


看到“媒体任务调度器启动”后保持终端运行。它负责到期的pending任务，不能代替后端HTTP服务。只有初次生成演示时可以暂不启动它；验收自动重试时必须运行。

本轮不需要 Redis 或 Celery Worker。inline 模式由 API 进程内的 BackgroundTasks 执行任务；它可以在发送响应后继续执行，但不是独立 Worker，API重启时未完成的工作不能靠它自动恢复。生成过程中先不要保存代码触发热重载。

**第三步：提交一条主图任务，检查202响应。**

在图片生成接口点击 **Try it out**，填入“低糖燕麦饼干”的商品 ID和已选主图方案 ID，点击一次 **Execute**。

预期返回202。记录 `id`，检查 `kind: "main_image_asset"`，`product_id`、`creative_plan_id` 与提交值一致。响应中的 `status` 通常为 `pending`，`attempts` 初始为0，`max_attempts` 默认为3，`result` 可以为空。

验收重点是“已创建任务记录并返回任务编号”，不是立即获得图片。不要连续点击POST等待图片出现；查询应使用下一步的GET接口。

**第四步：通过商品详情观察同一任务的状态和事件。**

调用 `GET /api/v1/products/{product_id}`，在 `generation_jobs` 列表中按第三步返回的 `id` 找到该任务。隔几秒重新点击GET的 **Execute**，查看同一条任务，而不是不断提交新任务。

| 字段 | 如何检查 |
|---|---|
| `status` | 从 `pending` 进入 `running`，最终成功、失败或取消；执行很快时可能看不到中间状态 |
| `attempts` | 每实际开始执行一次加1，不是刷新页面次数 |
| `started_at`、`finished_at` | 用于判断开始和本次执行结束时间；不单靠 `finished_at` 判定成功 |
| `locked_by` | 执行期间可显示执行者；结束清锁后可能为 `null` |
| `next_run_at` | 待重试任务的最早可执行时间，不代表已经有调度器负责届时执行 |
| `error` | 失败原因摘要；成功时应清空 |
| `events` | 查看 `event_type`、`message`、`worker_id` 和时间，了解过程 |
| `result` | 成功后保存素材信息，重点检查实际 `url` |

成功路径应能看到 `queued → started → succeeded` 事件，inline 执行的 `started` 事件中执行者为 `fastapi-background`。注意 `queued` 是事件名，任务等待状态的值是 `pending`，不要混写。

失败路径可能先出现 `retry_scheduled`，任务重新变为 `pending`；达到最大尝试次数后才变为 `failed` 并记录失败事件。`retry_scheduled` 不是终态，不能将它记录为“失败流程已结束”。

**第五步：验证成功任务的素材关联。**

任务 `status: "succeeded"` 后，继续在同一个商品详情中检查：

1. `result.url` 对应实际生成结果。
2. `generated_assets` 中有相同任务 ID的素材，`generation_job_id`、`creative_plan_id` 与本次任务一致。
3. 主图方案的 `content.generated_images` 中能找到对应URL；视频则是 `content.generated_videos`。
4. 按16.8.2的方法打开项目素材URL，真实图片可显示或视频可播放。

如果此前已完成16.8.2的素材审核，不必再次填写审核表单；这里重点检查任务与素材之间的关联。需要新生成视频时，对视频接口填写视频脚本 ID，重复第三步至第五步，预期 `kind: "video_asset"`。

**第六步：切换 Redis/Celery，验证独立 Worker。**

先等待当前 inline 任务结束，然后在调度器终端按 Ctrl+C 停止旧的inline调度器。打开新的 PowerShell 终端，在项目根目录启动已有的 Redis 服务：

```powershell
cd D:\atguigu\class\ecommerce-operation-assistant
docker compose up -d redis
docker compose ps redis
```

使用前面配置好的Redis端口和密码，不要重新创建数据库或改密码。在 `api/.env` 中修改：

```dotenv
TASK_QUEUE_BACKEND=celery
CELERY_TASK_DEFAULT_QUEUE=generation
```

同时核对已有 `REDIS_URL`，它必须与Docker暴露到本机的Redis端口和认证配置一致。API和Worker都是从本机启动时，使用本机可访问的地址；不要把Docker服务名 `redis` 当成本机主机名。不要在录屏中展示密码。

打开一个独立的 VS Code终端，从同一个课堂项目的 `api` 目录启动Worker：

```powershell
cd D:\atguigu\class\ecommerce-operation-assistant\api
uv run celery -A app.worker.celery_app:celery_app worker --loglevel=info --pool=solo -Q generation
```

这里使用单进程执行池进行Windows课堂演示。检查Worker启动信息中列出了 `generation.run_generation_job`，并出现就绪提示；终端保持运行。若自己使用其他队列名，环境变量与 `-Q` 后的名字必须一致。

再重启原API终端，仍使用第二步的Uvicorn启动命令；同时重新运行第二步的调度器启动命令，使调度器也读取新的celery模式。现在应保留三个终端：API、Worker和调度器。API和Worker必须读取同一数据库、同一份模型配置，并使用同一项目目录中的 `uploads`。只重启API而不重启Worker，不能保证Worker读取到修改后的环境变量。

**第七步：再次提交一条任务，确认由 Worker 消费。**

在Swagger按第三步提交一次主图任务，记下新的任务 ID。预期API返回202，同时Worker终端出现收到 `generation.run_generation_job` 的日志。

在商品详情中查询新任务，检查 `started` 事件的 `worker_id` 为 `celery-worker`，并按第五步核对成功素材。Worker日志中的Celery消息编号与数据库任务 `id` 是不同的编号，查询商品详情时始终用HTTP响应里的本地任务 ID。

Worker出现“task succeeded”日志，不一定表示图片生成成功：本服务可能捕获媒体调用异常并写入任务状态。最终必须检查数据库任务的 `status`、`error` 和素材结果。

**第八步：稳定验证“等待中的任务可以取消”。**

为避免任务刚提交就执行完，本轮先停止调度器，再在Worker终端按 Ctrl+C 正常停止Worker，等待它退出；保持Redis和API运行，API仍为 `celery` 模式。如果还有其他Worker消费 `generation` 队列，也要确保本轮没有消费者。

然后提交一条新的图片生成任务，记录任务 ID。此时API可以把消息放入Redis，商品详情中的任务应保持 `pending`。展开取消接口：

`POST /api/v1/products/{product_id}/generation-jobs/{job_id}/cancel`

填写当前商品 ID和刚才记录的本地任务 ID，直接 **Execute**，无需请求体。预期200，检查 `status: "cancelled"`、`next_run_at: null`，事件中有 `cancelled`。

重新启动Worker和调度器，等Worker处理队列消息，再次查询这个已取消任务：应仍为 `cancelled`，没有因该任务新增素材。执行函数会跳过非 `pending` 任务，因此队列里残留这条消息不等于取消失败。

如果取消的是已经完成的任务，预期400，而不是把成功记录改成取消。对正在执行的任务发起取消，只能按当前实现修改本地状态，无法保证供应商请求中止或已经产生的费用撤销；本轮以尚未执行的 `pending` 任务验证确定的取消效果。

**第九步：验证失败后的自动到期重试。**

有自然失败的任务时，记录它的ID并查看 `error` 和事件，修复实际原因。没有失败任务时，先运行新增的调度测试确认完整流程，不需要为了录课清空正常模型密钥或反复请求供应商：

```powershell
uv run pytest tests/test_generation_scheduler.py -q
```

该测试用替身模拟第一次媒体调用失败、到期后第二次成功，并检查任务ID不变、尝试次数增加，以及重复消息不能绕过退避时间；不消耗真实额度。

真实失败且 `attempts < max_attempts` 时，任务变回 `pending`，事件出现 `retry_scheduled`，并设置 `next_run_at`。首次失败后通常退避2分钟，第二次失败后退避4分钟。确认调度器仍在运行，等待响应里的实际到期时间；不要手工改数据库时间，也不要点击重试接口催促一个pending任务。

到期后观察调度器日志：inline模式由调度器执行；celery模式应看到Worker再次收到消息。同一个任务的 `attempts` 增加，事件新增 `started`。随后要么成功并关联素材，要么再次安排退避；达到 `max_attempts` 后应成为 `failed`，调度器不再自动选取它。

本章最多3次尝试包含第一次执行，不是“第一次加3次重试”。如果任务一直pending，先看 `next_run_at` 是否已到，再检查调度器、Redis、Worker和队列名；如果任务卡在running，则不属于这个pending扫描器的处理范围，需要排查执行进程和超时维护，不能靠不断点重试解决。

**第十步：对 failed 任务验证“同一个 ID 重试”。**

已有 `status: "failed"` 的任务且失败原因已修复时，记录它的 `id` 和 `attempts`，展开：

`POST /api/v1/products/{product_id}/generation-jobs/{job_id}/retry`

填写商品 ID和失败任务 ID，无需请求体，执行一次。预期202，检查响应的 `id` 与原任务一致，旧错误和执行锁被清理，事件新增 `retry_requested`。然后按第四步继续查询执行结果。

`attempts` 不会因为人工重试而清零；真正再次执行后会继续增加。如果此前已经达到 `max_attempts`，再次失败可能直接成为 `failed`，不能期待自动重新获得三次尝试。历史事件保留，便于查看失败、人工重试和再次执行的完整过程。

对 `succeeded` 或 `cancelled` 任务调用重试接口，预期400；对 `pending` 或 `running` 任务调用，可能返回202但不新增调度。这些都是状态边界，不应反复点击同一个按钮绕过。

**最后核对本章结果。**

| 验收点 | 完成标准 |
|---|---|
| inline 生成 | 202返回任务 ID，后续有执行事件，成功素材可访问 |
| Celery 生成 | 独立Worker收到消息，数据库任务实际成功并关联素材 |
| 查询能力 | 同一个本地任务 ID能查到状态、尝试次数、错误与事件 |
| 取消 | 无消费者时提交的pending任务可取消，Worker恢复后不会生成素材 |
| 失败与重试 | 到期任务被调度器再次执行，ID不变；达到上限成为failed，之后可人工重试 |
| 调度边界 | 调度器实际运行并扫描pending；不将running超时回收或供应商远端取消当成已完成 |

完成后保持API与Worker的配置一致。如果切回 `inline`，修改 `api/.env` 并重启API和调度器；Celery队列中已有的消息不会因修改模式自动消失。图片与视频的内容质量和人工审核仍按16.8.2进行，本节不重复填写。

### 17.8.3 本章小结

第17章让第16章的耗时媒体调用不再依附于一次 HTTP 连接：数据库任务记录保存业务事实，事件记录保存过程，inline 与 Celery 只是两种执行方式。至此第04篇完成“文本模型生成方案 → 媒体服务生成素材 → 后台任务可靠执行”的闭环。
